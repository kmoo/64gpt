## Decisions worth remembering

- **Pin pyrite64-mac to its latest tagged release** (v0.4.0 at time of
  writing; upstream is at v0.7.0). Early-dev engine, breaking changes —
  we upgrade deliberately, never accidentally.
- `core/` is C-style C++ in **`.cpp` files, kept flat** — both are hard
  requirements of Pyrite64's generated Makefile (only `.cpp` is
  compiled; directory symlinks are listed but not recursed into). We
  verified this in Pyrite64's source (`src/build/projectBuilder.cpp`,
  `data/build/baseMakefile.mk`), not just its docs.

## Gotchas (install)

- The v0.4.0 release dropped the `Pyrite64-Examples.zip` asset that
  earlier releases had — use the examples in the source clone instead.
- The source clone ships a `Pyrite64.app` at its root, but it's a stale
  stub (Feb 20 binary, empty `Resources/`); the **release zip's** app is
  the real, fully-assembled, signed one (Feb 25). Use the release asset.
- `curl` + `unzip` don't set `com.apple.quarantine`, so the app runs
  without Gatekeeper friction when fetched from the CLI.

## Gotchas (CLI build paths — v0.4.0)

Three build attempts taught us the CLI's path resolution is CWD-sensitive:

- From a directory **without** a `data/` template dir (our repo root), the
  build crashes: `filesystem error: in copy_file ... ["data/build/assets/
  font.ia4.png"]` — the asset-staging step writes to `data/build/` relative
  to the CWD.
- With CWD at the source clone root (`~/GitHub/pyrite64-mac`, which has
  `data/`) and a *relative* project path, the build succeeds — but resolves
  the project against the app bundle's `Contents/Resources/n64/...` copy,
  and the `.z64` lands there, not in the clone.
- **Rule until proven otherwise:** run the CLI from the clone root, and in
  M1 pass our game project as an **absolute** path, then verify the
  artifacts land in `game/` as expected.
