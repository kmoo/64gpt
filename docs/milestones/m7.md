# M7 — Living NPCs: Selena (planning — not started)

**Status: PLANNED.** Not started; specified here so the next build phase
has a concrete target instead of vibes. Synthesizes
`docs/ideas-m7-living-npcs.md` (both diagrams) into one architecture,
names the first character, and — the emphasis for this round — writes
down exactly what "train a bigger model" has to mean so H=256 lands in
the doc's own "magic zone" instead of just being a bigger version of the
same template-bound voice M4 already shipped.

## Why (unchanged north star)

Continuity of existence beats model size (`ideas-m7-living-npcs.md` Part
1). The win condition isn't prettier sentences, it's a character who
remembers you and reacts differently because of it. Everything below
serves that, including the training-rigor section — a bigger model that
still ignores its own conditioning is not more alive, just more
expensive.

## Architecture (the two diagrams, merged)

Part 1's diagram (World Simulator + NPC Database → Context Builder →
GRU) and Part 2's diagram (Dungeon System / 64GPT Brain / Music System
as peers under a World Simulation Layer) aren't two zoom levels of the
same thing — they imply different games (narrative sim vs. dungeon
crawler). Resolution: build the part every version of the game needs,
reserve a bus slot for the parts only some versions need, commit to
nothing that isn't load-bearing yet.

```
                         GAME ENGINE (Pyrite64)
                                  |
                    EVENT BUS  <----->  SHARED WORLD STATE
                                  |
        (any subsystem publishes events; any subsystem reads/writes
         state — this is the ONLY contract other subsystems must honor)
                                  |
      +----------------------+---+---+----------------------+
      |                                                      |
      v                                                      v
  NPC SYSTEM  (build now)                          [reserved, not built]
      |                                             DUNGEON SYSTEM · MUSIC SYSTEM
  NPC Database                                       (Part 2's boxes — same bus
  (Memories/Soul, per NPC)                            contract, zero code today;
      |                                               added later with no change
  Context Builder  <—— World State (Events)           to the NPC System)
      |         `—— NPC Database (Memories/Soul)
      v
  64GPT Brain  =  core/ as it exists today
  (frozen ngpt_load/reset/step/EOS, blob + model-type
   field, RSP matvec — untouched by any of this)
      |
  Final Dialogue
```

**Mapping onto real code:**

- **64GPT Brain = `core/`, unchanged.** No new engine work. Confirmed
  this session: `ngpt_reset(ctx, model, prompt)` already primes the GRU
  by feeding `prompt` character-by-character through the same vocab as
  generation (`core/ngpt_gru.cpp:145`, h-updates only, no emission).
  That means "condition on personality/memory/events" was never a
  missing feature — the frozen streaming API already accepts arbitrary
  text as its conditioning surface. This milestone changes what string
  the game builds, never the engine.
- **Event Bus + Shared World State = new, game-side** (`game/src/user/`,
  not `core/` — needs dynamic structures, so the no-heap/no-float rule
  doesn't apply here). Highest-leverage thing to build first: it's cheap
  and it's what keeps Dungeon/Music optional instead of foreclosed.
- **NPC Database = new, minimal: Selena (full) plus one thin placeholder
  identity** used only to stress-test the shared-model conditioning
  mechanism — see Evaluation Protocol below.
- **Dungeon System / Music System = documented, deferred.** No stub
  files — an unbuilt bus subscriber costs nothing; a stub invites
  premature interface decisions we'd have to walk back.

**Result (2026-07-16):** identity-swap divergence 0.966 vs mood-swap
divergence 0.816 (n-gram/trigram Jaccard, sampled not greedy — see
methodology note below). **Gate clears.** Full write-up, including two
false starts that mattered (a greedy-decode measurement artifact and an
undertrained-model near-miss) in `docs/spikes/identity-conditioning.md`.
Selena's corpus and H=256 training below are unblocked.

Added after this session's review of the plan: don't spend Selena's
~10MB corpus and real authoring time before de-risking the one
assumption everything else — the archetype system (M8), the villain and
bosses (M9), the whole town (M10) — depends on: **does text-priming
through the shared model actually carry an identity signal?** This is
the same discipline `docs/spikes/rsp-matvec.md` used before M6.1 bet a
milestone on the RSP kernel: prove the risky mechanism cheap, before the
real build commits to it.

Deliberately decoupled from H=256 — this spike runs on the **existing
H=128 model and pipeline** (already trained, already quantized, no new
goldens work) so it tests exactly one risk (does identity-conditioning
work) without also carrying the H=256 scale-up risk. If it passes at
H=128, Selena's real training run re-confirms it holds at H=256 as part
of the Evaluation Protocol below — that's a re-check, not a first test.

**Setup:**
- Two throwaway identities, no character bible, no voice pass needed —
  `id_a` / `id_b`. A few hundred lines each: pure combinatorial slot-fill
  against a couple of mood/context values is enough, this content never
  ships and doesn't need to sound like anyone. Fast enough to be a
  reasonable qwen-delegated task despite the earlier caution about
  delegating voice work — there's no voice to preserve here.
- Existing H=128 charset and schema; the current `ngpt_reset`-prompt
  priming mechanism, unchanged.

**Metric and gate** (same methodology as the Evaluation Protocol below,
run smaller and first): conditioning-ablation divergence — swap only the
identity tag, hold mood/context fixed, measure output divergence between
`id_a` and `id_b`; compare against divergence from a mood swap alone (the
in-mechanism baseline).

- **Clears the gate** (identity-swap divergence ≥ mood-swap divergence)
  → proceed to Selena's real corpus and H=256 training exactly as scoped
  below, with the core mechanism already evidenced, not just assumed.
- **Doesn't clear it** → do not write Selena's corpus yet. Redirect to
  the embedding fallback (an explicit learned embedding added alongside
  text-priming) as its own scoped design task first — a real
  `core/`-adjacent change with its own quantization and golden-vector
  work — before any character's corpus is authored against a
  conditioning mechanism that doesn't reliably differentiate.

**Cost, for comparison:** a few hundred lines × 2 identities, on the
already-proven H=128 pipeline — days, not the multi-week effort Selena's
full bible and 10MB corpus represent. This is the cheapest available
answer to "does this scale to a world," bought before the world's first
real character is written, not after. Once run, write up the result as
its own entry under `docs/spikes/`, matching the RSP kernel's precedent
— a ledger other milestones can point to, the same way M6.1 points back
to `rsp-matvec.md`.

## The first NPC: Selena

**Gated on the spike above passing.** Don't author the corpus below
until identity-conditioning is evidenced at H=128, not just designed.

Companion, not stationary NPC — she travels with the player rather than
waiting in one room. That's a better test of "continuity of existence"
than a cabin hermit: she has to react to events happening *around* the
player continuously, which is exactly why the Event Bus has to be real
now regardless of which game genre this becomes.

**Surface:** ~12 years old, friend to the main character, funny,
quirky, encouraging.

**Personality (draft — tune freely, these are starting sliders, not
canon):**

```
YOU ARE: Selena
Warmth:     90   (encouraging by default, notices when you're down)
Humor:      85   (quips, bad puns she's proud of, comic timing)
Impulsivity:70   (blurts things, corrects herself mid-sentence)
Bravery:    55   (talks brave, is not always brave — see Private)
Focus:      30   (tangents, gets distracted by shiny things)
```

**Public / Private / Secret / Fear / Desire** (the ideas doc's pushback
#4 — this is what makes a quirky kid read as a character, not a
mascot):

- **Public:** Fearless, always has a joke ready.
- **Private:** Gets scared like anyone else; hides it so the player
  doesn't worry.
- **Secret:** Rehearses her jokes under her breath before she says them
  out loud, so they land.
- **Fear:** That she's more annoying than helpful and gets left behind.
- **Desire:** To actually matter to the player — not be tolerated,
  *needed*.

**Companion-specific corpus shape.** Because she's present continuously,
most of her lines are short reactive banter, not monologue — this
should shape the corpus grammar directly:

- greeting / farewell
- item found / damage taken / low health
- combat banter (light, in-character, never breaks pace)
- quiet-moment lines (the "no quest, no reward, just a relationship"
  beat from the Rowan sketch — Selena's version of this is small talk
  that isn't plot-relevant)
- encouragement after a player failure
- a joke, sometimes landing, sometimes not (matches the Secret above)
- callback lines that reference something the player did earlier

**Deferred, deliberately:** rumor/gossip propagation (pushback #3) needs
more than one NPC to matter — out of scope until there's a second
character to gossip *to*. Memory corruption-over-time (pushback #2's
"rumor drifts from fact") is a stretch goal, not v1 — get one character
solid before adding decay dynamics.

## The conditioning contract

No change to `core/`'s frozen API. What changes:

**Schema, not prose.** Today's demo conditioning is three flat fields
cycled by buttons (`NPC=guard MOOD=angry EVENT=stole_sword`). The
Context Builder needs a compact tagged format the trainer and the
runtime both speak — proposed v1, subject to trainer-side iteration:

```
N:selena TR:2 M:cheerful C:item_found EV:found_gem|
```

(`N`=identity, `TR`=trust tier, `M`=mood, `C`=context category,
`EV`=last event, terminated by `|` same as today's convention.)

**Two hard constraints on this schema, both new for M7:**

1. **Charset.** M4's trained charset was 34 symbols inside the ≤96 cap
   (`docs/milestones/m4.md`) — tags, digits, colons, underscores are all
   plain ASCII so this should fit without growing the vocab table, but
   confirm explicitly once the schema is fixed. Nothing outside the
   trained charset has defined behavior.
2. **Prime-time budget.** Priming costs one GRU step per character, same
   as generation — at H=128/RSP that's ~4.8ms/char, H=256 will be more.
   A verbose personality/memory dump primed before *every line* directly
   eats the latency M6.1 just bought. **Target: keep the primed prefix
   short** (the compact schema above, plus at most 1-2 salient memory
   tags, not a memory dump) and **add prime-time as its own measured
   number** in the M7 acceptance criteria, not folded into steady-state
   ch/s.

**Forward note (M8):** the specific values here — `selena`, `cheerful`,
`item_found`, and Selena's five personality sliders in the section above
— are project *content*, not engine mechanism. M8 formalizes that
distinction into a manifest: these become the first entries in a
declared vocabulary (`schema_fields.mood`, `schema_fields.
personality_traits`, etc.) rather than values implicitly hardcoded in
prose. Nothing here needs to change for that — Selena's sliders and this
schema are exactly what M8's manifest is designed to capture.

## Building the "magic zone" model — this is the part that needs rigor

**Gated on the spike above.** Everything in this section assumes
identity-conditioning is already evidenced at H=128, not still an open
question — if the spike hasn't passed yet, resolve that first.

The concern driving this section: H=256 alone does not produce "magic."
M4's own numbers say why. That milestone shipped ~68K params (H=128,
V=34) trained on a 1.5MB generated corpus (1,503,198 chars, 12
NPC×MOOD×EVENT combos, 762–1129 distinct lines/combo) and *still*
recorded a documented conditioning miss in the goldens — WIZARD/CALM/
THEFT answering with festival imagery, right voice wrong event, kept
deliberately as "honest ~68K-param behavior." Doubling H to 256 without
also fixing what actually caused that costs nothing but ROM space: a
bigger model trained on the same narrow, template-bound corpus mostly
just memorizes the templates *more confidently*, which is the doc's own
"1.5M = diminishing returns" row, arriving early.

There are three separate levers here, and only one of them is "bigger."
Pulling only that one is the anemic outcome.

### 1. Corpus scale — a concrete target, derived not guessed

M4's ratio: 1,503,198 chars / ~68,000 params ≈ **22 characters of corpus
per parameter**. Holding that ratio at H=256's ~500K-800K params implies
roughly a **10-15MB corpus** — call it 10MB as the floor to build
toward. This is a starting target to validate empirically against the
val-loss curve and human eval, exactly like M4's own acceptance gate —
not a number to trust blindly and stop measuring.

### 2. Corpus *diversity* — the actual fix for "anemic," separate from size

Raw size alone repeats the M4 mistake at a larger scale. M4's grammar
was a small set of sentence templates with slot-filling for lexical
variety — that produces lots of distinct *strings* from few distinct
*shapes*, which is exactly what "template-bound" means and exactly what
a bigger model will still sound like if the underlying template library
doesn't also grow. Concrete instruction: **≥15-20 structurally distinct
sentence skeletons per context category** (not per NPC×mood×event triple
— per category, e.g. "encouragement after failure" needs 15-20 different
sentence *shapes*, each then getting lexical slot variety on top), so
structural variety compounds with lexical variety instead of standing in
for it.

Combinatorial matrix for Selena (bigger than M4's 12 combos, because one
deep character needs more emotional range than a roster of shallow
ones): **Mood {cheerful, worried, sassy, tender, embarrassed} × Trust
tier {new, growing, close} × Context {greeting, combat-banter,
item-found, damage-taken, quiet-moment, joke, encouragement, farewell}**
= 5 × 3 × 8 = **120 combos**. At M4-or-better density (≥150 distinct
lines/combo, up from M4's 762-1129 spread across only 12 combos — more
combos means each needs proportionally fewer lines, but M4's own
conditioning miss argues for *not* going below M4's per-combo density)
that's the volume that gets you to the 10MB+ target through genuine
combinatorial richness rather than padding.

### 3. Training regime — three changes from M4's recipe, not just a bigger H

- **Mask the loss over the primed prefix.** Compute loss only on the
  completion, not on reproducing the schema tags — otherwise the model
  spends capacity learning to echo `N:selena TR:2 M:cheerful` instead of
  learning voice. M4 didn't need this decision explicitly (flat 3-field
  prompts); M7's richer schema does. **Decide this before training, not
  after eyeballing bad output.**
- **Hold out conditioning combinations, not just lines.** M4 val-split
  held out lines within each of 12 seen combos — every combo was seen in
  training. For M7, hold out a slice of the 120-combo grid entirely
  (train on ~100, validate generalization on the other ~20) — this is
  the actual test of "generalizes, not memorizes," which is the ideas
  doc's own bar for feeling alive.
- **Add a conditioning-collapse guard to the acceptance suite.** Fixed
  event/mood, vary only identity/trust-tier/mood tag, verify the sampled
  output diverges by more than a noise threshold. Tiny conditioned
  models have a known failure mode of learning to ignore rarely-
  load-bearing input, especially under capacity pressure — this is the
  automated test that catches "everyone sounds the same" before it's a
  bug report. M4's WIZARD/CALM/THEFT miss is a live example of exactly
  the failure this guard exists to catch.

### Acceptance criteria — M4's pattern, plus new gates

Reuse exactly: val-loss threshold (recorded at tag time, same as M4) +
int8-vs-float top-1 agreement ≥95% on a fixed probe set + human eyeball
per condition. Add:

- **Conditioning-collapse guard** (above) — automated, not eyeball-only.
- **Prime-time budget** — measured on the RSP path for a realistic
  conditioning string; target under ~1s before the first generated
  character streams (protects the latency M6.1 built).
- The full metric set (effective-diversity tracking, per-axis
  conditioning-ablation divergence, repetition/mode-collapse check, the
  identity-generalization decision gate) is specified in **Evaluation
  Protocol** below — that section is the actual gate, this list is the
  short form.

### Iteration loop (bounded, so this doesn't run forever)

Train → sample the full 120-combo grid → score against the Selena bible
above (voice authenticity, conditioning correctness, no repetition
loops) → patch the worst-scoring cells with targeted corpus additions →
retrain. **Cap at 3 rounds** before escalating to a rethink of the
schema or corpus structure itself — mirrors the cap-2-retry-then-
escalate discipline already used for delegated work in this project.

### Delegation plan (lead-mode)

Not delegate-able, lead-authored only: the character bible, the
conditioning schema, the acceptance thresholds, the training-loop
decisions above (masking, held-out combos) — architecture and
bit-exact/numeric decisions are excluded from delegation by the
project's own lead-mode rule.

Delegate-able once the bible + schema are fixed: bulk template/variant
generation under a tight contract. **Learn from the M4 precedent before
writing that contract** — `corpus_gen` (task 004) was escalated after 3
qwen-worker attempts producing fixed sentences with no slots, and the
contract itself had unsatisfiable size arithmetic (734KB max vs. 1MB
min). For M7: hand-author a real seed set first (30-50 lines in genuine
Selena voice, covering a spread of the 120-combo grid) and embed those
verbatim as in-contract examples — voice is too specific to delegate
from a bare description, but it delegates fine from strong examples.

## Evaluation protocol — measuring instead of guessing

Val loss and int8-vs-float agreement (M4's bar) don't catch two real
failure modes at this scale: **mode collapse** (technically correct,
says the same line every time) and **conditioning collapse**
(technically varied, ignores its own tags). Both need a metric, not an
eyeball.

### Effective diversity, not raw byte count — MEASURED, round 1

Templated text carries much lower entropy per character than natural
language — 15MB from 3 sentence skeletons is less real signal than 5MB
from 20. Track, alongside the 10MB byte target: distinct-trigram
coverage per combo, and unique-line ratio after near-duplicate
collapse. If these plateau while corpus size keeps climbing, the
generator is padding, not diversifying — that's the signal to go widen
the template library (lever 2 above), not generate more volume.

**Result on Selena's round-1 corpus** (`trainer/ngpt_trainer/
effective_diversity.py`, task 005): distinct-trigram count is
**flat across a 6x volume increase** — 1818 at per_combo=50 (6,000
lines) vs. 1822 at per_combo=300 (36,000 lines). This is exactly the
plateau this section warns about: raising the skeleton count per
context to ≥15-20 (this milestone's lever 2) fixed *sentence-shape*
repetition, but the underlying *word vocabulary* those skeletons draw
from is still narrow enough that character-trigram diversity saturates
almost immediately — natural-language trigram variety comes from
lexical breadth, not sentence-shape count alone. unique-line ratio also
drops steadily as volume grows (0.75 → 0.55 across the same range),
confirming later draws are increasingly exact repeats within a bounded
combinatorial space, not new content.

**Conclusion: per_combo=300 (this round's actual training scale) is
already past the point where more repetition helps** — climbing toward
the 10MB target by raising per_combo further would inflate duplicate
count, not real diversity, and would waste training capacity
memorizing exact repeats. The correct next lever, if a future round
wants more genuine content, is widening the *lexical* vocabulary within
each skeleton (more synonym/phrasing variety per slot), not more draws
from the current one. Recorded here rather than silently chasing a
byte target that this measurement shows is already saturated.

### The identity-generalization re-check (first proof already happened — see the spike)

The spike above is the actual first test of the shared-model-vs-per-NPC-
weights question, run cheap at H=128 before Selena's corpus existed.
This subsection is what happens at Selena's real scale: **confirm the
spike's result still holds at H=256, on real (if still deliberately
thin) second-identity data** — a re-check, not a first proof, and much
lower-stakes since the mechanism is already evidenced.

- Selena gets the full ~10MB corpus. Add one **thin placeholder second
  identity** — a few hundred lines, deliberately *not* proportional to
  Selena's — spread across a handful of the 120 combos. Its only job is
  to force the `N:` tag to matter during training at the real H=256
  scale; it is not a second character and gets no bible.
- Keep 100% of the placeholder's data in training — there isn't enough
  of it to both train and hold out meaningfully, and its own
  generalization isn't what's being tested. Differentiability is.
- **Metric — conditioning-ablation divergence, per axis** (same
  methodology as the spike, now with real per-axis numbers instead of
  just identity-vs-mood). Generate matched pairs that differ in exactly
  one tag (swap only `N:`, hold mood/trust/context fixed; then only
  `M:`; then only `TR:`; then only `C:`). Measure output divergence per
  pair using **sampled generation (temperature + multiple draws), never
  greedy decode** — the spike's own false start: greedy collapses onto
  one global mode on any corpus with multiple valid completions per
  condition (which this corpus has, by construction, same as M4's), and
  read as a total conditioning failure (div=0.000) when the sampled
  metric on the same model showed the mechanism working fine. Fixed
  metric: character-trigram Jaccard divergence (n-gram overlap), not KL
  — cheaper, no probability distributions needed, already validated
  discriminating in the spike. Report as a per-axis table: identity,
  mood, trust, context.
- **Decision gate:** identity-swap divergence should be at least
  comparable to mood-swap divergence, same bar as the spike. **Clears
  it** → H=256 confirms the spike, future NPCs stay cheap (a few hundred
  lines each, not a full corpus) — proceed to M8's archetype system with
  confidence. **Misses it at this scale even though the spike passed at
  H=128** → treat as a genuine surprise worth investigating before M8
  (something about the bigger model or Selena's much larger corpus is
  interfering with the signal that held at small scale) rather than
  assuming the spike's result simply transfers.

### Repetition / mode-collapse check

Sample N generations per combo at the shipped sampler settings, measure
n-gram overlap across the samples. High self-overlap within a combo —
even with a good val loss — reads as "vending machine," not alive; this
is the specific failure the ideas doc's opening pages warn about
(linguistic quality without continuity of existence).

### Regularization and split, stated precisely

- Selena: combo-level holdout (train on ~100 of the 120 combos,
  validate generalization on the rest) — tests unseen-*combo*
  generalization, not just unseen lines within a seen combo.
- Placeholder identity: no holdout, per above.
- Weight decay + recurrent dropout as tunable knobs if the val-loss
  curve bends upward earlier than M4's did — the standard fix at this
  data:param ratio, before reaching for "shrink the model back down."

### Run logging

Every training round records: corpus version/hash, seed, hyperparams,
val loss, int8-vs-float agreement, the per-axis divergence table, and
the self-similarity score — the same discipline M4 used to record its
exact numbers at tag time. This is what makes the 3-round iteration cap
(above) meaningful: each round's record has to show the *specific*
prior failure got fixed, not just "retrained, looks better."
