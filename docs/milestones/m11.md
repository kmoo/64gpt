# M11 — Town, dungeon loop, and the portability release (IN PROGRESS — gossip mechanism + boot self-test switch landed, rest planned)

**Status: IN PROGRESS (2026-07-18).** Depends on M8 (archetype/instance
system), M9 (compositional conditioning), and M10 (three-tier cast,
procedural instantiation, the bad guy — renumbered from the original
M10 slot on 2026-07-17 when compositional conditioning became M9; see
`docs/milestones/m9.md`). This is where the pieces become the actual
game — town hub, shops, the pub, side-quest areas, a full dungeon loop
with the full cast — and where "other people can use this" stops being
an aspiration and becomes a released, documented, *tested* seam.

**What's actually landed so far (section 2 only — honestly scoped, not
the full milestone):**

**1. Gossip, finally.** `WorldState` gained a single gossip slot
(`currentGossip()`/`setGossip()`, `game/src/user/WorldState.h`/`.cpp`) —
"" until a real player-caused event sets it, no history or decay (M11's
own plan calls for "keep it simple for v1"). The real trigger lives in
`DialogueDemo.cpp`: reaching trust tier 2 with Shadewrath or Korrath for
the FIRST time (a genuine new high-water mark, checked against
`SaveData::current`, not every re-visit to an already-maxed NPC) publishes
to both `EventBus` and `WorldState::setGossip()`. `NpcService::eventFor()`
(new, pure, host-tested) decides which EV: value a compositional-scheme
NPC's prompt actually carries: gossip if the occupation is a trained
"gossip hub" (`NpcService::isGossipHub()` — true only for `pub_patron`
and `villager`, the two occupations the corpus was actually trained on
for this; "EVERY VILLAGE NEEDS A GOOD GOSSIP. THAT'S ME." is a literal
pre-existing villager line), otherwise the ordinary per-interaction event
— every other occupation's behavior is completely unchanged.

Deliberately did NOT route gossip through every character. `EventBus::
lastTag()` is already broadcast globally to every active NPC's prompt
(a pre-existing M7 mechanism), so publishing a gossip tag naively would
have fed an out-of-distribution EV: value to every OTHER trained
character (Selena, guard, Bram/Fergus/Kragan, Shadewrath, Korrath) the
moment gossip went live — worse than not building this at all. Gating on
`isGossipHub()` at the call site keeps the blast radius to exactly the
two occupations trained to handle it.

Corpus: `trainer/ngpt_trainer/cast_corpus.py` gained `GOSSIP_EVENTS`
(`"shadewrath_allied"`, `"korrath_pleaded"` — must match `WorldState::
GOSSIP_EVENTS` byte-for-byte, cross-checked by a pinned-value test same
discipline as `test_guard_instances.py`'s `EXPECTED` dict), and
`GOSSIP_HUB_OCCUPATIONS`. 30% of pub_patron's and villager's combos
(`GOSSIP_FRACTION`) draw a gossip tag instead of a direct
`EVENTS_FOR_CONTEXT` event, and get a mandatory (not probabilistic)
secondhand-reaction line appended from `_GOSSIP_LINES` — phrased as
hearsay ("I HEARD", "THEY SAY", "WORD IS"), since these two occupations
never witnessed the event themselves.

On-screen proof: a gossip-hub archetype slot (fixed roster or dungeon-
generated) shows a `NEWS` suffix when it's carrying live gossip — an
exact, screenshot-checkable flag, the same discipline `MET TR:N` uses to
make the save system's persistence visible rather than trusting subjective
judgment of generated text quality.

Host tests: `test_context_builder.cpp` (`WorldState` gossip slot),
`test_npc_service.cpp` (`isGossipHub`/`eventFor` truth tables),
`trainer/tests/test_cast_corpus.py` (7 new tests: vocabulary parity,
hub-gating both directions, mandatory gossip-line inclusion, direct-event
coverage preserved). Retrain: `trainer/make_m11_blob.py`, same H=320
production mix as M10 plus the gossip-tagged combos — 2 new goldens
(one prompt per gossip tag, chosen deliberately rather than randomly
sampled, to guarantee both tags are covered on real hardware without
padding the self-test's boot time further than necessary).

**Retrain result: val loss 0.0992** (M10's shipped 0.0995, M10 v1 0.0980,
M9 0.0985, M9.2 0.1036) — essentially flat versus M10, no measurable
regression from adding gossip-tagged combos to 2 of 7 compositional-cast
occupations. Int8-vs-float top-1 agreement 0.9771, comfortably above the
0.95 gate. The generalization check (3 held-out (occupation, descriptor)
combos never seen anywhere in training) produced 3/3 non-degenerate
output, unaffected by the gossip addition — expected, since gossip only
touches the EV: axis, orthogonal to the OCC:/D: axis that check probes.

**The gossip mechanism itself produced real, on-distribution output**:
the Korrath-tagged golden (`P:woman D:cheerful OCC:pub_patron
R:close_friend M:tender C:encouragement EV:korrath_pleaded|`) generated
`"...WORD IS THE KNIGHT FINALLY SPOKE HIS TRUE WISH. IT'S MYSELF. I'M
GLAD WE'RE FRIEND."` — `"WORD IS THE KNIGHT FINALLY SPOKE HIS TRUE
WISH."` is one of `_GOSSIP_LINES["korrath_pleaded"]`'s actual authored
lines, reproduced verbatim mid-generation. This is the concrete proof
the EV:<gossip_tag> → secondhand-reaction association was learned, not
just present in the training data. **Same honest caveat as every other
M9/M10 compositional-cast character**: overall coherence remains mixed
(both gossip goldens show the same garbled-clause pattern documented for
Shadewrath/Korrath since M10 — this is the model's existing capacity
limit at H=320 with this many trained voices, not something gossip made
worse or better).

**Hardware-verified**: ROM rebuilt (`trainer/make_m11_blob.py` →
`game/rawfs/model.bin` + `game/src/user/selftestGolden.h`), booted in
Ares with `NGPT_SELFTEST_ENABLED=1` (the default, see item 2 below):
**SELFTEST PASS, RSP ON, XCHK PASS** for all 29 goldens (15 curated + 6
compositional-cast + 2 gossip + 3 Shadewrath + 3 Korrath).

**2. The boot self-test build switch (2026-07-18)** — unrelated to
gossip mechanically, landed the same session while investigating this
milestone's own goldens-count growth. `DialogueDemo.cpp` gained
`#define NGPT_SELFTEST_ENABLED` (default `1`): the CPU-vs-RSP cross-
check and full golden replay every prior milestone's `SELFTEST PASS`
proof depends on. Setting it to `0` skips straight to `BOOT_READY`
(still installing the real RSP backend first — a fast-boot build isn't
slower to *play*, only faster to *boot*), and the two status lines print
`SELFTEST SKIPPED (RELEASE BUILD)` / `XCHK SKIPPED (RELEASE)` instead of
a stale PASS/FAIL claim. This toolchain has no actual Debug/Release
build-type distinction (`n64.mk` uses one fixed `-O2` flag set, no
`-DNDEBUG` — checked directly, not assumed); this is a deliberate
source-level toggle instead, same convention as the file's existing
`NGPT_ATTRACT_MODE`. Full design rationale, and the binding rule that
`NGPT_SELFTEST_ENABLED` **must stay `1`** for any milestone-verification
or `versions/` build: `docs/adr/0002-no-debug-release-build-type-
source-level-switch-instead.md`.

## Why

Every prior M7-M10 milestone proved one mechanism at a time on a small
slice of content. M11 is the integration test for all of them at once,
at the scale the actual game needs — and it's the milestone where
portability gets a real acceptance bar instead of a doc that asserts it.

## Engineering plan — with the engineer hat on

### 1. Build out the full town cast, using M8/M9's mechanism, not new mechanism

Shops, the Irish pub, side-quest areas — thin-tier archetype instances
per M8/M9, placed by hand (they're static, not dungeon-generated) rather
than seeded from a level generator. No new subsystem: this is content
authoring against an already-proven mechanism, which is exactly the
point of having built M8/M9 first.

**Partially pulled forward into M10 (2026-07-17):** `pub_patron` and
`wizard` from this list, plus `blacksmith` and `villager` (not
originally planned here), landed in M10's session alongside Shadewrath
— cheap enough, and shared that session's retrain rather than paying for
a second one (`docs/milestones/m10.md`). **Still open, M11 scope:**
`shopkeeper` and `damsel` from the original list here, plus placing any
of these archetypes by hand in an actual town scene (M10 only added them
to the training corpus and the archetype mechanism — none are wired
into `DialogueDemo.cpp`'s NPC-selection UI yet, in the town or
otherwise).

### 2. Gossip, finally — the feature the ideas doc called "the killer
feature" back at the start of this project's M7 planning

Deferred at M7 for lack of a second character, out of scope at M8/M9/M10
for lack of a full town. By M11 the Event Bus, Shared World State, and a
real multi-NPC cast all exist — this is where they pay off. Concrete
shape: an event the player causes (defeated a boss, helped a town NPC)
publishes to the bus; the pub — thematically the natural gossip hub —
is where a `pub_patron` or the bartender's conditioning string picks up
an `EV:` tag referencing that event, so patrons "know what happened" a
scene or two after it happened, without any dedicated gossip-propagation
engine. Keep it simple for v1: event → world state → nearby NPCs'
conditioning references it. Full rumor drift/corruption (pushback #2's
"the rumor changes as it spreads") stays a stretch goal, not required
here.

### 3. Dungeon loop integration

Wire M10's procedural instantiation into the actual level-generation
loop end to end: town → unlock a dungeon → generated levels with
thin-tier NPCs and occasional mid-tier bosses → the bad guy appears at
defined points → return to town, state persists (the bad guy remembers,
town NPCs may reference what happened via the gossip mechanism above).

### 4. Portability packaging

Extract and document, separately from the dungeon crawler's specific
content:

- The schema DSL spec (from M8) and the compositional feature vocabulary
  (from M9), as a genre-agnostic contract
- The Event Bus / Shared World State / NPC Database shapes
- The three-tier cast model (M10) as a reusable pattern, not dungeon-
  crawler-specific
- The training pipeline (corpus → schema-conditioned training → prefix-
  loss masking → quantize → export → goldens) as a repeatable recipe
- A **porting guide**: exactly what a new project must supply (its own
  field vocabulary, its own character bibles, its own corpus) versus
  what it gets for free (the streaming API, the priming mechanism, the
  archetype/tier system, the compositional feature mapping, the training
  pipeline shape)

### 4a. The meta-schema, formalized

M8 introduced the manifest (`characters[]`, `archetypes[]`,
`schema_fields{}`, including `personality_traits` as a declared
vocabulary rather than hardcoded trait names) as the artifact a project
fills in; M9 added the compositional feature vocabulary on top. M11 is
where that becomes the actual porting-guide deliverable rather than a
shape described in earlier milestones' prose: publish it as its own
versioned spec, with the dungeon crawler's manifest (Selena, the bad
guy, the bosses, the town archetypes) as the worked reference example a
new project can diff against.

### 4b. The manifest-update skill

A tool that operates on the manifest: validate an edit (schema
conformance, per M8's DS review — every declared trait/mood/context
actually used, nothing orphaned) → regenerate the affected corpus slice
(hand-authored seed + qwen-delegated bulk generation, M7's delegation
pattern, M9's LLM-judge quality gate) → retrain → run the full
acceptance suite (val loss, int8-vs-float, per-axis conditioning-
ablation divergence, M8's within-archetype divergence, M9's LLM-judge
score, the capacity-degradation check against full-tier baselines) →
regenerate blob + goldens + selftest header only if every gate passes;
refuse and report the specific failing gate otherwise. The
refuse-on-failure behavior is what actually enforces the capacity
split-trigger below — a skill that only monitors and reports doesn't
stop a bad manifest edit from shipping a degraded shared model.

**Must be parameterized on project config/paths, not hardcoded to
64GPT's own layout** (`corpus/selena/`, `trainer/`, this repo's
directory names) — that parameterization is what makes it the same
skill file a second project could point at their own manifest, rather
than a 64GPT-only tool wearing a portability costume. This is a direct
requirement of the portability proof in §5 below: if the skill can't run
unmodified against the ported archetype's manifest, portability isn't
proven, it's asserted.

**One design decision to make before building it, not after:** full
retrain vs. continued training from the last checkpoint when a manifest
edit only touches one character or archetype. Full retrain is cleaner
for the project's existing goldens-never-drift discipline but gets more
expensive as the cast grows through M8-M11; continued training is
cheaper but risks the checkpoint quietly diverging from what the goldens
were pinned against. Pick one and record why — this is exactly the kind
of numeric/reproducibility call the project's own lead-mode rule reserves
for the lead, not something to leave implicit in the skill's
implementation.

### 4c. Limits — translating "how big can this get" into numbers

- **Engine-fixed, not negotiable:** `NGPT_GRU_MAX_HIDDEN` (256 as of M8;
  M9 may raise this to ~320, see `docs/milestones/m9.md`),
  `NGPT_GRU_MAX_VOCAB=96` cap raw model capacity regardless of cast size.
- **Blob size is not the constraint.** The shared model stays a few
  hundred KB whether the manifest has 3 characters or 30 — don't budget
  cast size against ROM space, budget it against capacity degradation
  instead.
- **The real limit is the capacity split-trigger** defined below, not a
  hard character-count ceiling.
- **Planning numbers for this game's roster**, translating that trigger
  into practice: full-tier (Selena, the bad guy) — 1-3 realistically,
  ~10MB corpus each, expensive in authoring time rather than engine
  budget. Mid-tier (talking bosses, the pub owner) — 3-6. Thin-tier
  **archetype types** (`guard`, `shopkeeper`, `wizard`, `damsel`,
  `pub_patron`) each need their own corpus slice too, so also bounded —
  start around 6-10 distinct types. **Instances per archetype are
  effectively free** (a seed, per M8) — that's where "a few dozen main
  talkable characters" gets absorbed cheaply, since most of those dozens
  are instances, not new corpus. M9's compositional features should make
  this even cheaper: instances sharing profile/relationship features
  share learned capacity, not just a seed.

### 5. The portability proof (see Data Science Review — this is the
acceptance bar, not optional)

Port one archetype to a deliberately different genre and confirm it
works through the unmodified toolkit: same `core/`, same Event Bus code,
same training pipeline, only the corpus and field vocabulary swapped.
Recommend a lightweight version — not a second full game, just one
archetype (e.g., a sci-fi "engineer" instead of a fantasy "guard") with
its own small corpus and schema vocabulary, proven bootable — as the
falsifiable version of "this is portable," rather than resting the claim
on documentation alone.

## Data Science Review — reviewing the engineering plan above

**"Portable" has to be falsifiable, and the plan above already knows
that — hold the line on it.** The porting guide is necessary but not
sufficient; documentation describing a seam is not evidence the seam
holds under someone else's assumptions. The archetype-swap proof in
section 5 is the actual test — treat it as a required acceptance
criterion, not a stretch goal that quietly gets cut under schedule
pressure, because "we documented it" and "it works for someone who
isn't us" are different claims and only the second one is the one being
promised.

**The capacity question raised at M8/M9/M10 comes to a head here, and
M11 needs a decision rule, not just monitoring.** By this milestone the
shared model carries: Selena (full), the bad guy (full), at least one
boss (mid), and however many archetype instances the full town needs
(thin, but numerous — "a few dozen" per the original brief). This is
the largest real test of the shared-model-vs-per-NPC architecture
question this whole project line has been circling since the first
conversation about M7. Concrete recommendation: define the split
trigger numerically now, before the full cast is trained — e.g., "if
adding the full archetype roster degrades Selena's or the bad guy's
held-out divergence by more than X% versus their M7/M9 baselines, split
into two shared models (named-cast model + archetype model) rather than
keep pushing one model." Decide X now, while it's a design choice, not
after training run 3 when it's a scramble.

**The gossip feature is new *content* built on old *mechanism* — treat
it that way in testing.** Nothing about publishing an event to nearby
NPCs' conditioning strings is architecturally new by M11 (the Event Bus
and conditioning mechanism are both already proven), so this doesn't
need a new evaluation category. It does need the existing conditioning-
ablation divergence check re-run with `EV:` values that reference
gossiped-about events specifically, to confirm the mechanism that was
validated on direct events (M7) still holds for events an NPC learns
about secondhand — a real but narrow extension of an existing test, not
new infrastructure.

**Sequencing risk worth naming out loud.** M8 through M11 each assume
the previous milestone's empirical results (divergence thresholds,
per-tier corpus budgets, the capacity-degradation baseline) are in hand
before the next one starts content work. If schedule pressure compresses
these into parallel work, the numbers this whole plan depends on
(derived, not guessed, per the M7-M10 reviews) won't exist yet when
they're needed. The milestone split only pays off if each milestone's
data science review actually gates the next milestone's start — treat
the gates as real, not as a documentation formality.
