## Why

M7 through M11 built and proved a full toolkit's worth of mechanism —
the schema DSL (M8), the compositional feature vocabulary (M9), the
three-tier cast model and procedural instantiation (M10), the Event Bus
/ Shared World State / gossip pattern (M11) — all of it built and tested
against exactly one game (the dungeon crawler). M14 is where that stops
being a claim ("this could work for other genres") and becomes something
actually demonstrated: a real second use of the toolkit, proven to boot,
not just documented as possible.

## Engineering plan — with the engineer hat on

### 1. Portability packaging

Extract and document, separately from the dungeon crawler's specific
content:

- The schema DSL spec (from M8) and the compositional feature vocabulary
  (from M9), as a genre-agnostic contract
- The Event Bus / Shared World State / NPC Database shapes
- The three-tier cast model (M10) as a reusable pattern, not dungeon-
  crawler-specific
- The training pipeline (corpus → schema-conditioned training → prefix-
  loss masking → quantize → export → goldens) as a repeatable recipe
- A **porting guide**: exactly what a new project must supply (its own
  field vocabulary, its own character bibles, its own corpus) versus
  what it gets for free (the streaming API, the priming mechanism, the
  archetype/tier system, the compositional feature mapping, the training
  pipeline shape)

### 1a. The meta-schema, formalized

M8 introduced the manifest (`characters[]`, `archetypes[]`,
`schema_fields{}`, including `personality_traits` as a declared
vocabulary rather than hardcoded trait names) as the artifact a project
fills in; M9 added the compositional feature vocabulary on top. M14 is
where that becomes the actual porting-guide deliverable rather than a
shape described in earlier milestones' prose: publish it as its own
versioned spec, with the dungeon crawler's manifest (Selena, the bad
guy, the bosses, the town archetypes) as the worked reference example a
new project can diff against.

### 1b. The manifest-update skill

A tool that operates on the manifest: validate an edit (schema
conformance, per M8's DS review — every declared trait/mood/context
actually used, nothing orphaned) → regenerate the affected corpus slice
(hand-authored seed + qwen-delegated bulk generation, M7's delegation
pattern, M9's LLM-judge quality gate) → retrain → run the full
acceptance suite (val loss, int8-vs-float, per-axis conditioning-
ablation divergence, M8's within-archetype divergence, M9's LLM-judge
score, the capacity-degradation check against full-tier baselines) →
regenerate blob + goldens + selftest header only if every gate passes;
refuse and report the specific failing gate otherwise. The
refuse-on-failure behavior is what actually enforces the capacity
split-trigger below — a skill that only monitors and reports doesn't
stop a bad manifest edit from shipping a degraded shared model.

**Must be parameterized on project config/paths, not hardcoded to
64GPT's own layout** (`corpus/selena/`, `trainer/`, this repo's
directory names) — that parameterization is what makes it the same
skill file a second project could point at their own manifest, rather
than a 64GPT-only tool wearing a portability costume. This is a direct
requirement of the portability proof in §2 below: if the skill can't run
unmodified against the ported archetype's manifest, portability isn't
proven, it's asserted.

**One design decision to make before building it, not after:** full
retrain vs. continued training from the last checkpoint when a manifest
edit only touches one character or archetype. Full retrain is cleaner
for the project's existing goldens-never-drift discipline but gets more
expensive as the cast grows through M8-M11; continued training is
cheaper but risks the checkpoint quietly diverging from what the goldens
were pinned against. Pick one and record why — this is exactly the kind
of numeric/reproducibility call the project's own lead-mode rule reserves
for the lead, not something to leave implicit in the skill's
implementation.

**Decision (2026-07-28/29, overnight session, explicit go-ahead from
Luke to make this call rather than leave it blocked): full retrain,
always.** Reasons:

1. **Goldens-never-drift is this project's single most consistently
   enforced invariant** — `tests/vectors/`, `game/rawfs/model.bin`, and
   `game/src/user/selftestGolden.h` are regenerated only by trainer
   scripts (CLAUDE.md's own hard constraint), and every milestone's
   SELFTEST/XCHK ritual exists specifically to catch drift between what
   was proven bit-exact and what actually ships. Continued training
   from a checkpoint means the shipped weights are now path-dependent
   on training history (which edits happened in what order, from which
   prior checkpoint) rather than reproducible from the manifest + seed
   alone — a strictly weaker reproducibility guarantee than every other
   artifact in this codebase gets.
2. **Blob size is not the constraint (§1c already established this)**,
   and neither, so far, is wall-clock retrain cost: every real training
   run this project has measured (M8 through tonight's M13 experiments)
   has landed in the tens-of-minutes-to-low-hours range on a single
   consumer GPU (MPS), not a cost that forces a cheaper-but-riskier
   path yet.
3. Continued training's real advantage (cost) only starts to matter
   once the cast is large enough that a full retrain becomes genuinely
   painful — that's a future optimization to revisit **if and when**
   retrain cost is measured to actually be a bottleneck (§1c's planning
   numbers: 1-3 full-tier, 3-6 mid-tier, 6-10 thin-tier archetype
   types), not a default to build in from day one on a guess. The
   manifest-update skill's v1 implementation should do a full retrain
   unconditionally; revisiting this decision needs its own real cost
   data, not a re-guess.

### 1c. Limits — translating "how big can this get" into numbers

- **Engine-fixed, not negotiable:** `NGPT_GRU_MAX_HIDDEN` and
  `NGPT_GRU_MAX_VOCAB=96` cap raw model capacity regardless of cast
  size. **Re-verified 2026-07-29 against current `core/ngpt.h` (this
  section had gone stale)**: `NGPT_GRU_MAX_HIDDEN` is **1024**, not
  ~320 — M12's K-chunked RSP kernel (ported from the hardware-verified
  `spike/rsp-matvec-ktile` branch) raised the actual engine ceiling to
  1024 with explicit sign-off, to test whether more capacity fixed the
  coherence gap. It didn't (M12's own controlled result: worse val
  loss, 44→5 ch/s) — M12.1 shipped back at **H=320**, and that's what
  every model in this project actually trains at today, but the engine
  itself could go up to 1024 again if a future, de-noised signal
  (`docs/ideas-coherence-rescue-plan.md` phase 6) ever justified it.
  Don't confuse "the engine could" with "the shipped model does."
- **Blob size is not the constraint.** The shared model stays a few
  hundred KB whether the manifest has 3 characters or 30 — don't budget
  cast size against ROM space, budget it against capacity degradation
  instead.
- **The real limit is the capacity split-trigger** defined below, not a
  hard character-count ceiling.
- **Planning numbers for this game's roster**, translating that trigger
  into practice: full-tier (Selena, the bad guy) — 1-3 realistically,
  ~10MB corpus each, expensive in authoring time rather than engine
  budget. Mid-tier (talking bosses, the pub owner) — 3-6. Thin-tier
  **archetype types** (`guard`, `shopkeeper`, `wizard`, `damsel`,
  `pub_patron`) each need their own corpus slice too, so also bounded —
  start around 6-10 distinct types. **Instances per archetype are
  effectively free** (a seed, per M8) — that's where "a few dozen main
  talkable characters" gets absorbed cheaply, since most of those dozens
  are instances, not new corpus. M9's compositional features should make
  this even cheaper: instances sharing profile/relationship features
  share learned capacity, not just a seed.
- **Concrete decision, deferred from M11's own Data Science Review**:
  define the numeric capacity split-trigger — e.g. "if adding the full
  archetype roster degrades Selena's or the bad guy's held-out
  divergence by more than X% versus their M7/M9 baselines, split into
  two shared models (named-cast model + archetype model) rather than
  keep pushing one model." M11's full-cast retrain should have generated
  the actual divergence numbers this decision needs — check `docs/
  milestones/m11.md` before guessing X from scratch.

  **Decision (2026-07-29, using real numbers already on record rather
  than guessing X from scratch):**

  - **Metric: per-character held-out FLOAT-phase val loss** (new tool,
    `trainer/ngpt_trainer/capacity_monitor.py`'s
    `held_out_loss_for_subset()` — predicate-based, e.g.
    `lambda prompt: "N:selena" in prompt`, so it isn't hardcoded to this
    project's own tag scheme), computed for Selena and the bad guy
    specifically — NOT the aggregate val loss or the conditioning-
    ablation divergence table, both of which are computed over the
    whole combined val set and are exactly what let M8's real
    capacity-dilution problem hide behind a healthy-looking aggregate
    number until guard/Selena coherence was checked directly.
  - **NOT the QAT-phase val loss**, deliberately. `m13_mechanism4_results/
    baseline_seedA.json` vs `baseline_seedB.json` (same config, only the
    seed differs) put FLOAT val loss noise at ~0.15% (0.1341 vs 0.1339)
    but QAT val loss noise at ~29% (0.1413 vs 0.1818) — QAT's own
    demonstrated seed instability (M13's still-open follow-up) would
    swamp any percentage-based trigger defined on it. Float loss is the
    metric with a demonstrated-small noise floor; use that one.
  - **X = 5%.** Calibrated against M8's own real capacity-dilution
    failure (`docs/milestones/m9.md`'s Why section) — the exact scenario
    this trigger exists to catch again: Selena's held-out val loss moved
    0.0964→0.0991→0.1026 as guard's corpus share went 1.7%→6.7%→12.6%,
    single-step increases of +2.8% and +3.5% (cumulative +6.4%) that
    were already visibly bad enough (opposite-direction guard/Selena
    curves) to motivate M9's whole redesign. 5% sits above float's
    ~0.15% seed-noise floor (a real signal, not noise) and inside that
    historical trajectory — catching a repeat of the same trend before
    it fully compounds to M8's demonstrated-bad endpoint, not only after.
  - **Operational, real numbers (2026-07-29):**
    `trainer/m14_capacity_baseline.py` (reproduces `make_m12_1_blob.py`'s
    exact shipped corpus config — M12.1, not M11.1's stale pre-fix
    numbers — with combo-level holdout extended to Shadewrath as well as
    Selena, float-phase only per this section's own decision) ran to
    completion:

    | | held-out combos | held-out float val loss |
    |---|---|---|
    | Selena (`OCC:companion`) | 20 of its own | **0.1356** |
    | Shadewrath (`OCC:villain`) | 24 of 120 total | **0.1763** |
    | (aggregate, for reference) | — | 0.1510 |

    These are the real `baseline_loss` numbers to pass into
    `CapacityCheck(...)` going forward — the 5% trigger above is now
    checkable against an actual number, not just defined in the
    abstract. Next time this cast's corpus grows (a new archetype, a
    manifest edit), re-run `held_out_loss_for_subset()` against Selena's
    and Shadewrath's own val-pair subsets and compare: if either
    degrades by more than 5% versus 0.1356 / 0.1763 respectively, that's
    the split-trigger firing for real.

    One real bug was found and fixed before it could corrupt this
    result: an earlier version of `held_out_loss_for_subset()` took a
    `device` parameter that crashed when passed `"mps"` after MPS
    training, since `train_corpus_conditioned` always returns a
    CPU-resident model regardless of training device — caught via a
    real MPS regression test (`test_works_correctly_after_mps_training`)
    before the baseline run reached that code path, fixed by removing
    the parameter entirely. A second real gap found in the same review:
    `manifest_update.py`'s own val split was a random line-level
    shuffle, not this project's established combo-level holdout
    discipline (`docs/milestones/m7.md`) — fixed, TDD'd, both are on
    `main`.

    **Caveat on the run's own reported wall-clock time**: the script
    printed "trained in 39224s" (~10.9 hours) — almost certainly
    inflated by the machine sleeping mid-run (a lid-close/reopen
    happened during this exact run), not real GPU-busy training time.
    Not a claim about actual training cost; the val-loss numbers
    themselves are unaffected by wall-clock timing.

### 2. The portability proof (see Data Science Review — this is the
acceptance bar, not optional)

Port one archetype to a deliberately different genre and confirm it
works through the unmodified toolkit: same `core/`, same Event Bus code,
same training pipeline, only the corpus and field vocabulary swapped.
Recommend a lightweight version — not a second full game, just one
archetype (e.g., a sci-fi "engineer" instead of a fantasy "guard") with
its own small corpus and schema vocabulary, proven bootable — as the
falsifiable version of "this is portable," rather than resting the claim
on documentation alone.

**Result (2026-07-28/29, overnight session): the mechanism ported clean;
the coherence claim is not (yet) demonstrated.**

Two separate claims, kept separate rather than conflated:

1. **Mechanism transfer: TRUE, and falsifiably so.** A real second-project
   manifest (`manifests/scifi_freighter.json`) with zero shared
   vocabulary with the dungeon crawler validated clean through the
   unmodified `validate_manifest_cli.py`
   (`trainer/tests/test_manifest_validate.py::test_no_undeclared_or_orphaned_values_in_scifi_freighter_manifest`,
   pinned as a regression test, not a one-time check). Its corpus
   generator (`trainer/ngpt_trainer/scifi_engineer_corpus.py`) reuses
   `npc_service.prompt_fields()` and the compositional schema
   unmodified. Training (`trainer/m14_portability_proof.py`) ran through
   the plain `train_corpus_conditioned`/`qat_finetune` pair -- the real
   shipped pipeline shape, zero mechanism-code changes, checkpointing
   from tonight's own new capability confirmed working under real (not
   toy-scale) training. Every one of these is the actual falsifiable
   test §2 asks for, and every one passed.

2. **Coherence: inconclusive, not a claimed win.**

   | | lines | invented/line |
   |---|---|---|
   | guard (existing archetype) | 8 | 4.375 |
   | engineer (new sci-fi archetype) | 8 | 5.125 |

   Both numbers are far above the shipped model's ≤1.00 target -- but
   that's expected, not a portability failure: this experiment
   deliberately used a thin corpus (540 guard pairs + 135 engineer
   pairs, no Selena/cast/shadewrath/korrath/elowen context, a random
   15% holdout rather than combo-level) to keep the proof lightweight,
   per §2's own "lightweight version" framing. This project's own
   established finding (M8 through M12.1) is that thin, low-density
   corpora produce garbled output regardless of genre or mechanism --
   corpus density, not the compositional schema itself, is what drives
   coherence. **The comparison that matters for portability is
   guard-vs-engineer under IDENTICAL thin conditions, not either number
   against the production ≤1.00 bar**: 5.125 vs 4.375 is close enough
   (engineer ~17% worse, same order of magnitude, not catastrophically
   different) that the new genre's archetype doesn't fail in some
   qualitatively different way than the established one under the same
   starved-corpus conditions. That's a mild positive signal, not proof
   the new archetype would read as genuinely coherent at production
   corpus density -- that would need its own real corpus investment
   (`guard_corpus.py`-scale authoring, not this proof's deliberately
   thin 135 pairs) and its own retrain, out of scope for tonight.

**Honest bottom line:** the portability PROOF (does the unmodified
toolkit accept and train a new genre's archetype with zero
mechanism-code changes) succeeded. The portability PRODUCT (would a
player experience the sci-fi engineer as a coherent voice) was never
in scope for this lightweight version and remains untested -- don't
read the coherence numbers above as a verdict on that question, they
weren't designed to answer it.

## Data Science Review — reviewing the engineering plan above

**"Portable" has to be falsifiable, and the plan above already knows
that — hold the line on it.** The porting guide is necessary but not
sufficient; documentation describing a seam is not evidence the seam
holds under someone else's assumptions. The archetype-swap proof in
§2 is the actual test — treat it as a required acceptance criterion, not
a stretch goal that quietly gets cut under schedule pressure, because
"we documented it" and "it works for someone who isn't us" are
different claims and only the second one is the one being promised.

**The capacity split-trigger decision should use real data by the time
this milestone starts, not be guessed from scratch.** M11's full-town-
cast retrain (its own DoD item on the quality push) is exactly the
"grow the shared model, watch Selena/bad-guy divergence" experiment
this decision rule needs — pull those numbers forward into this
milestone's planning rather than re-deriving them.

**Sequencing risk worth naming out loud.** This milestone assumes M11's
empirical results (the capacity-degradation baseline, the quality-push
outcome) are in hand before this milestone's own content work starts.
If schedule pressure compresses the two into parallel work, the numbers
this whole plan depends on won't exist yet when they're needed — the
same warning M8-M11's own reviews have carried forward at every step.
