# M9 — Compositional conditioning: fixing capacity dilution (planning — not started)

**Status: PLANNED.** Depends on M8 (archetype/instance system, shipped
ROM v1.3). **Renumbered 2026-07-17**: this slot was originally "Procedural
cast: bosses, the villain, and dungeon-generated NPCs" — that content is
unchanged in substance but moved to `docs/milestones/m10.md` (which
itself moved to `docs/milestones/m11.md`), because compositional
conditioning is a *foundational* rewrite the three-tier system should be
built on top of, not alongside.

This milestone replaces M8's opaque per-character identity tag
(`N:selena`, `N:guard#1001`) with a small set of **reusable,
compositional descriptive features** (`girl, age:12, sassy, VILLAGER` +
a relationship-closeness label like `best_friend`) — conditioning that
*generalizes* across characters sharing traits, instead of *memorizing*
one dedicated association per raw id. It also generalizes the RSP matvec
kernel to a formula instead of a third hand-derived hardcode, and
replaces manual N64-screenshot eyeballing with an LLM-judge quality gate
for text coherence at the trainer/host level.

## Why

M8's own measured evidence is the reason this milestone exists. Three
retrains at guard density 3→12→24 (share of the combined corpus
1.7%→6.7%→12.6%) tracked guard coherence and Selena's val loss moving in
**opposite directions**: 1/4→2/4→4/4 clean guard goldens, Selena val
loss 0.0964→0.0991→0.1026 (`docs/milestones/m8.md`, Data Science
Review). That's not noise — it's every new opaque identity tag competing
for its own slice of a fixed, shared parameter budget, because nothing
about `N:guard#1001` and `N:selena` is shared or reusable by the model.
Add a fifth archetype, a fiftieth guard instance with a genuinely
different personality, or M10's bad guy, and the same tax applies again
and again, with no ceiling in sight except "stop adding characters."

The fix, proposed mid-M8-session by Luke: stop conditioning on opaque
ids and condition on **compositional features** instead — occupation,
age/gender, a personality descriptor derived from the same 5 trait
sliders M8 already has, and a relationship-closeness label. A second
sassy 12-year-old girl NPC then conditions on nearly the same tokens
Selena already does; the model learns feature→voice associations that
generalize, not per-id memorization that only grows. Full design
rationale and worked examples: `docs/ideas-m7-living-npcs.md` Part 3
and its "refined" addendum (recorded live during this milestone's
planning).

## Engineering plan — with the engineer hat on

### 1. The compositional feature vocabulary

Four dimensions, each a small closed vocabulary (matching the project's
existing `MOODS`/`CONTEXTS`/`TRAITS` convention — declared once, not
hardcoded per-character):

- **Occupation** — `villager, guard, merchant, wizard, damsel,
  pub_patron, blacksmith, healer, noble, bandit, farmer, innkeeper`.
  Pulled from M11's (formerly M10's) already-written town-cast list, not
  invented fresh. M8's `guard` archetype is direct evidence this axis
  alone already produces a coherent, reusable voice signal — this
  formalizes what M8 already proved informally.
- **Age + gender, combined into one natural token** — child/teen →
  `girl`/`boy`, adult → `woman`/`man`, elder → `elderly woman`/`elderly
  man`. Reproduces Luke's own "12 years old" → "girl" example directly.
- **Personality descriptor** — derived from the *same 5 trait sliders*
  M8 already has (`NPCDatabase::TRAITS`: warmth, humor, impulsivity,
  bravery, focus), via ordered blend rules (e.g. `humor≥70 and
  impulsivity≥60 → "sassy"`), falling back to a single dominant-trait
  word if no blend matches. **Calibration requirement**: Selena's real
  personality (`{warmth:90, humor:85, impulsivity:70, bravery:55,
  focus:30}`, `NPCDatabase.cpp`) must map to `"sassy"` — the exact word
  from Luke's own worked example. No new trait vocabulary is invented;
  this is a second interpretation layer over the one M8 already trained.
- **Relationship closeness label** — a single derived scalar (mean of
  familiarity/affection/trust/respect; fear handled as a separate
  modifier, not averaged in, since a feared-but-trusted relationship
  reads differently than a low-trust one and shouldn't cancel out into
  one number) bucketed into named tiers: `stranger → acquaintance →
  neutral → friend → close_friend → best_friend`. Reproduces "1.0 (best
  friend)" directly. Relationship *type* (friend/family/rival/customer/
  employer) is a separate, orthogonal categorical field per
  `docs/ideas-m7-living-npcs.md` Part 3's original spec.

`npc.id` (e.g. `"guard#1001"`) stays as an internal game-engine lookup
key — `NPCDatabase` indexing, save state, `memorySlot` — it does **not**
need to be what's fed into the conditioning string anymore. The frozen
`ngpt_reset` API is untouched; only what `ContextBuilder`-equivalent
code writes into the primed string changes.

### 2. NPC service mapping — Python first, C++ port once validated

`trainer/ngpt_trainer/npc_service.py` (built this session): the mapping
function `conditioning_features(profile, relationship) -> str`, plus
`personality_descriptor()`, `age_gender_token()`, `relationship_label()`.
Python-only for now — mirrors M8's own sequencing (`guard_instances.py`
prototyped before `NPCDatabase.cpp`'s guard bits existed). The C++ port
(extending `ContextBuilder` or a new `game/src/user/NpcService.cpp`,
cross-checked against the Python implementation the same way
`test_guard_instances.py` checks against real compiled `NPCDatabase.cpp`
ground truth) is real M9 work, gated on the vocabulary being validated
by the corpus/LLM-judge pipeline first — don't port a mapping that's
still being tuned.

### 3. Relationship state: persistent, and randomized for testing

Storage: rides on `NPCDatabase::NPC.memorySlot` (already reserved,
already empty, waiting for exactly this — M8 explicitly deferred its
meaning to "M9+"). Five axes (familiarity, affection, trust, respect,
fear), 0.0–1.0 each.

`random_relationship_state(seed)` / `random_npc_profile(seed)`: seed-
deterministic via xorshift32 — same RNG discipline as `core/
ngpt_sample.cpp` and M8's `spawnInstance` (seed 0 remaps to 1, same
fixed-point rule). **"Randomize" here means seed-deterministic, not
truly nondeterministic** — a deliberate reading consistent with every
other RNG use in this project (M4's sampler, M8's instance jitter), not
a silent scope decision; recorded explicitly since "randomize" could be
misread otherwise.

The update/decay system that turns `EVENT_PLAYER_STOLE_ITEM` into
`affection -0.3, trust -0.4` (the missing piece `docs/ideas-m7-living-
npcs.md` Part 3 already flagged) is the second real subscriber
`EventBus.h`'s own docstring anticipated ("add it when a second real
subscriber actually needs to be pushed to instead of pulling
`lastTag()`"). Design, not build, this milestone — implementation is
DoD-tracked below but not required for the mechanism to be provable.

### 4. Corpus generation: don't limit it, and don't repeat M8's mistake

M8's guard corpus started too thin (density 3) and needed two full
retrains to reach acceptable quality — a real, measured cost (three ~20
minute CPU training runs plus review time). M9 corpus work starts
generously dense instead of iterating up from thin. Organize authoring
around **feature combinations**, not raw character ids — a
sassy-12-year-old-girl-villager OPENER pool that any matching NPC draws
from, authored once, reused by every character with those features. This
is the real methodology shift `docs/milestones/m8.1.md` (LLM-generated
corpus vs. template grammar) already flagged as worth testing — M9 is
where it actually gets tested, since compositional conditioning needs
many feature combinations covered, a better fit for LLM generation than
M8's per-archetype isolated-dispatch template grammar.

**Local-only, open-weight models for bulk generation** — qwen/mistral
via `~/bin/opencoder`, never Claude/proprietary APIs for corpus text.
**Prerequisite, not yet resolved**: per this session's own finding
(`opencoder-model-setup.md` memory), DeepSeek-Coder and Mistral are
currently *not actually downloaded* on this machine — only
`Qwen2.5-Coder-{0.5B,7B,14B}` are cached and working; the configured
models 401 from HuggingFace. Fix HF auth, or re-point
`OPENCODER_TYPE=code`'s `MODEL_7B`/`MODEL_14B` at the confirmed-working
Qwen2.5-Coder models, before any bulk M9 corpus dispatch — this blocks
real corpus generation, not just a nice-to-have.

Isolated per-feature-combination dispatches, not batched — M8's own
finding (`guard_corpus.py`'s module docstring) was that an
all-characters-in-one-prompt dispatch causes voice collapse even with
explicit differentiation instructions; isolated dispatches produced
genuinely distinct output. Same discipline applies here, one level more
granular (per feature combo, not per character id).

### 5. LLM-judge evaluation — replacing manual eyeballing for text quality

M7/M8 both learned "gates pass numerically ≠ output is coherent" — the
project's automated acceptance gates (val loss, int8-vs-float agreement,
divergence thresholds, repetition self-similarity) don't catch textual
incoherence; only reading the actual generated text does, and that's
been a manual, slow, Ares-screenshot-dependent process. M9 replaces the
*manual* part (not the *principle*) with an LLM-judge pass: a local
qwen/mistral model scores a sample of (feature-combo, generated line)
pairs on a small rubric — grammatical coherence, matches the stated
personality/voice cues, not a near-duplicate of other samples for the
same combo — run at the trainer/host level, no ROM boot required, so it
can cover far more combinations than a human could eyeball on a boot
screen. **The N64 boot test (SELFTEST PASS, XCHK) stays for hardware
bit-exactness only** — that's what it's actually good at proving, and
it was never a text-quality check to begin with.

**Open question, explicitly not resolved by this doc**: whether the
LLM-judge's scores actually correlate with human judgment on this
project's specific voice bar. Same skepticism M7/M8 applied to numeric
gates applies here too — spot-check a sample of LLM-judge scores against
a human read before trusting the pipeline at scale, don't just assume an
LLM grading LLM output is automatically reliable.

### 6. RSP kernel generalization — a formula, not a third hardcode

**The math** (derived from the real `.bss` layout in `game/src/user/
rsp_ngpt.S`, verified to reproduce the exact H=256 numbers):

```
params(H, V) = 3H² + 4HV + 6H + V          V = 66 (current vocab)
DMEM(H)      = 2600 + 4H + 8192/H  bytes   budget: 4096B
```

| H | params | DMEM used | headroom |
|---|---|---|---|
| 256 (current) | ~266K | 3,656B | 440B |
| **320 (M9 target)** | **~394K** | **~3,906B** | **~190B** |
| 368 (hard wall) | ~506K | 4,096B | **0B — unsafe** |
| 473 (800K target) | ~800K | ~4,664B | **impossible, over budget** |

The README's prior "~500K+ params" claim for H=256 was wrong (corrected
as part of this work — the real number is ~266K, verified against the
actual `model.bin` byte count in M8's training logs). The 500-800K "magic
zone" from `docs/ideas-m7-living-npcs.md` Part 1 needs H≈368-473; the
current tile-based RSP kernel physically cannot reach the top of that
range (`H=473` needs ~570 more bytes of DMEM than exist, before any
safety margin) and can only graze the bottom of it (`H=368`) with zero
engineering margin — a real risk given RSPQ dispatch overhead isn't
fully counted in the `.bss`+`.data` figure this formula reproduces.

**M9 target: H≈320 (~394K params)** — a real ~50% capacity increase over
M8's H=256 with actual margin, generalizing the exact tiling strategy
the two existing spikes already proved (`docs/spikes/rsp-matvec.md`
H=128, `docs/spikes/rsp-matvec-h256.md` H=256): `W_TILE` tile-depth
computed from `H` at build time (`tile_rows ≈ 2048/H`, an integer, so
the real per-H constant needs computing precisely, not just plugging
into the idealized formula above), `W16_BUF`/`H_BUF` scaling as `2H`
each, `OUT_TILE` scaling with tile-depth. **Reaching the actual 500-800K
magic zone needs a genuinely different DMEM strategy** (smaller
intermediate representation, a different streaming approach, something
beyond parametrizing the current kernel) — documented here as a real
follow-up, not attempted in M9 so it doesn't block the corpus/cast work
that's this milestone's real priority.

### 7. Model-type versioning

`NGPT_GRU_MAX_HIDDEN` (frozen at 256 since M2) needs to become 320 (or
stay parametric) for the blob format and `core/` engine caps — a
frozen-interface change per this project's own hard-constraints list,
meaning it needs explicit sign-off before touching `core/`, same gate
every prior frozen-API change has gone through.

- The three-tier cast system (full/mid/thin), procedural dungeon-level
  NPC seeding, save/load determinism for procedural instances, the bad
  guy — this is what M9 *used to be*; unchanged in substance, moved to
  `docs/milestones/m10.md`, which now explicitly depends on M9's
  mechanism rather than M8's opaque tags
- Full town cast, gossip, portability packaging, the manifest-update
  skill — `docs/milestones/m11.md` (formerly M10)
- Reaching the full 500-800K "magic zone" param count — needs a new RSP
  DMEM strategy beyond formula-generalizing the current tiling approach;
  documented above as a real follow-up, not silently dropped
- A general-purpose relationship-decay engine — the update/decay system
  is designed (§3) but building the full `EventBus`-driven mutation
  pipeline for every conceivable event type is scoped down to "prove the
  mechanism on a handful of events," not an exhaustive system

## Data Science Review — reviewing the engineering plan above

**The capacity-dilution hypothesis needs its own falsification test, not
just a plausibility argument.** The whole premise of this milestone is
that compositional features reduce the M8 density-vs-Selena-quality
trade-off — that's a hypothesis, backed by a reasonable mechanism
(shared traits share capacity), not yet measured data. The DoD above
requires re-running M8's exact density-sweep methodology under the new
scheme specifically so this claim gets checked against real numbers
before M10/M11 assume it's true, the same discipline M8 itself used
(measure the trade-off, don't guess it).

**The LLM-judge is a new *kind* of measurement, and needs the same
skepticism the project already applies to every other metric.** Val
loss, divergence, and repetition self-similarity have all, at different
points, passed numerically while the actual text was garbled (M7, M8)
— an LLM-judge is not exempt from the same failure mode; it can score
plausibly while being systematically wrong about this project's specific
voice bar. Spot-check against human judgment before treating it as a
trusted gate, not after.

**The personality-descriptor blend rules are hand-authored heuristics,
not derived from data — say so, and validate the one case that matters
most.** The Selena calibration check (`{90,85,70,55,30} → "sassy"`) is
necessary but covers exactly one point in a 5-dimensional space. Before
trusting the blend table for corpus generation at scale, run it across
the full personality-range space M8's archetypes already define (e.g.
`GUARD_ARCHETYPE`'s ranges) and eyeball whether the resulting labels
feel right for a guard, not just for Selena — the sample-generation step
in the DoD should include this check explicitly, not just prove the
mechanism runs.

**The H≈320 target trades safety margin for capacity, and the margin
number itself deserves one more sanity pass before hardware work
starts.** ~190B of headroom (vs. H=256's 440B) is real but thinner than
the currently-shipping kernel's own margin — worth re-deriving the exact
integer tile-depth (not the idealized `8192/H` continuous approximation)
and confirming the real `.bss`+`.data` total from a built `.elf`, the
same way the H=256 spike verified its own budget against actual section
sizes rather than hand math alone (`docs/spikes/rsp-matvec-h256.md`).
Do this before committing to H=320 as final, not after the first crash
on real hardware.

**Sequencing risk, inherited from M8/M10/M11's own reviews.** This
milestone's numbers (the H=320 target, the capacity-dilution reduction
hypothesis, the LLM-judge rubric) all need to actually be measured
before M10 (three-tier system) and M11 (full town cast) can safely
build on them. If those milestones start content work before M9's own
Data Science Review items are resolved, they inherit unvalidated
assumptions — the same warning M10/M11's own docs already carry forward
from the original M8-M9-M10 review chain.
