# M8 — Archetypes: the portability substrate (planning — not started)

**Status: PLANNED.** Depends on M7 (Selena + the thin-identity
conditioning experiment). This is the milestone where the system stops
being "one bespoke character" and becomes *a system for characters* —
which is simultaneously what the dungeon crawler's "few dozen main
talkable characters" needs and what makes 64GPT usable by someone else's
game, even if their genre and cast are nothing like this one.

**Gate:** M7's identity-generalization decision gate must have cleared
(identity-swap divergence ≥ mood-swap divergence) before this milestone
proceeds as scoped below. If it didn't clear, M8 starts from the
embedding fallback instead of text-priming archetypes — see Data Science
Review.

## Why

The original design question this project wrestled with — one model per
NPC, or one model conditioned on identity — was answered "shared model"
on architectural grounds, then turned into an actual experiment in M7.
M8 is where that answer has to hold up under real load: not one named
companion plus a thin stress-test identity, but dozens of instances
across a handful of *types*. If the shared-model bet only works for a
cast of two, it isn't the right bet for a dungeon crawler with a town
full of guards, shopkeepers, and wizards. This milestone is also where
"portable" stops being a claim and starts being an actual seam in the
code — a second project's engineer should be able to read one document
and know exactly what they'd have to supply.

## Engineering plan — with the engineer hat on

### 1. Generalize the schema DSL: separate mechanism from content

M7's schema (`N:selena TR:2 M:cheerful C:item_found EV:found_gem`) has
64GPT-demo-specific *values* baked into the field vocabulary
(`M:cheerful`, `C:item_found`) — and, caught during this session's
review, Selena's five personality sliders (`Warmth`, `Humor`,
`Impulsivity`, `Bravery`, `Focus`) are baked into prose the same way.
Both need the same fix: the reusable part is the *shape* — identity tag,
a small number of categorical/numeric conditioning fields, an event tag,
`|` terminator, priming through the trained charset via the frozen
`ngpt_reset` API — never the specific words. The mood list, the context
categories, and **the personality trait names themselves** are all
project content, declared once, not assumed.

### 1a. The manifest — the actual artifact, not just a spec in prose

Two layers, and the split matters for portability:

- **Meta-schema (fixed, ships with the toolkit):** `characters[]`,
  `archetypes[]`, `schema_fields{}`, the three tiers (full/mid/thin —
  see M9). This is mechanism.
- **Project manifest (one JSON file per game, e.g. the dungeon
  crawler's):** the actual values filling that shape.

```json
{
  "version": 1,
  "schema_fields": {
    "mood": ["cheerful", "worried", "sassy", "tender", "embarrassed"],
    "context": ["greeting", "combat-banter", "item-found", "quiet-moment"],
    "trust_tiers": [0, 1, 2, 3],
    "personality_traits": ["warmth", "humor", "impulsivity", "bravery", "focus"]
  },
  "characters": [
    {
      "id": "selena", "tier": "full",
      "personality": {"warmth": 90, "humor": 85, "impulsivity": 70, "bravery": 55, "focus": 30},
      "bible": {"public": "...", "private": "...", "secret": "...", "fear": "...", "desire": "..."},
      "corpus_ref": "corpus/selena/", "memory_persistence": "full"
    }
  ],
  "archetypes": [
    {
      "id": "guard", "tier": "thin",
      "personality_ranges": {"warmth": [20, 50], "humor": [10, 40]},
      "corpus_ref": "corpus/archetypes/guard/", "name_gen": "fantasy_male_names.txt"
    }
  ]
}
```

`personality_traits` is declared here exactly like `mood`/`context`
already were — a project building a horror game or a sci-fi game
supplies its own trait axes (`menace`, `paranoia`, whatever), and
`characters[].personality` / `archetypes[].personality_ranges` are
validated against whatever the project declared, not against Selena's
five sliders. This manifest is also the concrete artifact M10's porting
guide should point at — "supply a file shaped like this" is a testable
instruction; "supply your own character bibles" was not.

A tool to edit this manifest (validate → regenerate corpus → retrain →
verify → ship) is specified in M10, once there's enough cast for
maintaining it by hand to actually hurt.

### 2. Archetype / instance system — the "generic type / default / random" question, answered for real

This is the direct implementation of the interface floated at the start
of this project's M7 planning (character id / name / slug / generic
type / default-or-random).

- **Archetype** = a `personality_ranges` entry (not a fixed point, keyed
  by the manifest's declared `personality_traits`) + a corpus slice + a
  name-generation rule. Examples for the dungeon crawler: `guard`,
  `shopkeeper`, `wizard`, `damsel`, `pub_patron`.
- **Instance** = archetype + a seed → deterministic personality jitter
  within the archetype's ranges (xorshift32, same PRNG already used by
  the M4 sampler — one RNG discipline for the whole project) + a
  generated or assigned name + its own NPC Database memory slot,
  initially empty.
- The conditioning string's `N:` field becomes `archetype:seed` (e.g.
  `N:guard#4f2a`) rather than a hand-authored identity string. Two
  `guard` instances share the archetype's corpus and personality range
  but resolve to different jittered values, so they read as individuals,
  not clones — this is the mechanism M7's thin-identity experiment was
  built to validate before betting a whole cast on it.

### 3. Pets: explicitly out of the generative pipeline

Pets are not part of "a few dozen main talkable characters" — don't
spend shared-model capacity or corpus budget on them. Give them a
separate, much cheaper canned/templated reaction system (barks, not
generated lines). This is a scoping decision worth recording, not an
oversight: it protects the shared model's limited capacity for
characters that actually carry conversation, and it's the right tool
for "wags tail" versus "delivers a line."

### 4. Prove it: one archetype, end to end, in the existing demo

Ship one archetype (recommend `guard` — the dungeon crawler needs many)
with 3-4 seeded instances in the current demo scene. Walking-skeleton
bar: each instance should read as a variation on "guard," distinct from
the other guard instances *and* from Selena — not a clone of either.
This is M8's bootable-ROM proof, same discipline as every prior
milestone.

## Definition of done

- [ ] Meta-schema written as a standalone document (manifest shape:
      `characters[]`, `archetypes[]`, `schema_fields{}`), separated from
      any one game's field vocabulary or trait names
- [ ] Dungeon crawler's project manifest started: `schema_fields`
      declared (mood, context, trust tiers, personality traits), Selena
      expressed as a `characters[]` entry, `guard` as an `archetypes[]`
      entry
- [ ] Archetype/instance data model implemented in the NPC Database
      (archetype template + seeded jitter + generated name + memory slot)
- [ ] `guard` archetype corpus authored (size/density TBD — see Data
      Science Review, not a blind reuse of M7's placeholder number)
- [ ] Pets scoped out of the GRU pipeline; separate bark system stubbed
      or documented as explicitly deferred
- [ ] 3-4 seeded `guard` instances distinguishable from each other and
      from Selena, verified by the within-archetype divergence metric
      (Data Science Review)
- [ ] ROM boots, SELFTEST PASS, demo scene shows Selena + 2 guard
      instances in the same session
- [ ] Docs: this file finalized with real numbers, schema spec published,
      README status row, tag `m8`

## What M8 deliberately does not do

- The dungeon crawler's full cast (shopkeeper/wizard/damsel/pub_patron
  archetypes) — one archetype proven first, the rest are M9/M10 content
  work using the same mechanism
- Procedural dungeon-level NPC spawning — M9
- The bad guy / talking bosses (these are a different tier, not
  archetype instances) — M9
- Actually publishing the toolkit for outside use — M10

## Data Science Review — reviewing the engineering plan above

**The whole archetype premise is conditional on M7's gate, and that
needs to be stated as a hard dependency, not a hope.** If M7's
identity-swap divergence came in below mood-swap divergence, text-
priming alone isn't carrying identity signal reliably, and building an
archetype/instance system on top of it just multiplies a mechanism that
doesn't work. In that case M8 should start from the fallback noted in
M7 — an explicit learned embedding added alongside text-priming — with
archetype IDs as embedding-table indices. Mechanically this is mostly
transparent to the Context Builder (still emits `N:guard#4f2a`, just
also looks up an embedding), but it *is* a real `core/`-adjacent
architecture change with its own quantization and golden-vector work,
and M8's scope should be understood to grow if this branch is taken.
**Decide which branch M8 is in before writing corpus.**

**New metric needed: within-archetype instance divergence.** M7's
per-axis divergence metric tested identity vs. mood vs. trust vs.
context — all *between*-category comparisons. M8 needs a *within*-
category one: do two seeded instances of the same archetype (`guard#1`
vs `guard#2`) actually diverge, or does the personality jitter get
washed out the same way an untrained identity would? This is a new row
in the divergence table, not a variant of an existing one — measure it
before calling the archetype system proven.

**Don't reuse M7's "few hundred lines" placeholder budget uncritically.**
That number was a deliberately-thin stress-test value, chosen to be
*hard to differentiate on*, not a recommended per-archetype minimum.
Once M7 actually runs, it will produce a real measured threshold for
"how little data still clears the divergence gate" — M8's archetype
corpus budget should be derived from that number (with margin, since
archetypes need to support several jittered instances, not one fixed
identity), not carried over as a guess. If M7 hasn't produced that
number yet, M8 shouldn't start corpus work off an assumed size.

**Schema conformance is a testable invariant, not just documentation —
treat it that way from the first manifest.** Once `personality_traits`
(and `mood`/`context`/`trust_tiers`) are declared rather than hardcoded,
it becomes possible — and cheap — to write a test that every
`characters[].personality` and `archetypes[].personality_ranges` key
actually exists in `schema_fields.personality_traits`, same discipline
as M4's corpus-generator grammar/charset/length invariants. Write this
test alongside the manifest, not after the first typo'd trait name
silently trains a model that ignores a slider nobody meant to drop.

**Capacity is a shared, finite resource — start tracking it now, not at
M10.** Every archetype added to the training corpus competes for the
same ~500-800K parameters Selena's voice depends on. One archetype is a
small load; by M10 the plan calls for dozens of instances across several
archetypes plus a full-tier bad guy. Recommend logging Selena's val-loss
and divergence numbers *every time* M8 retrains with a new archetype
added, specifically to catch catastrophic interference (Selena's voice
quietly degrading as the shared corpus grows) at the first sign of it,
rather than discovering it after the full cast is built at M10.
