# M11.1 — Isolated retrain + full genericization + one new axis (planning — not started)

**Status: PLANNED (2026-07-22).** Depends on M11 (`docs/milestones/
m11.md`), which shipped with an honest negative result: a combined
retrain (2 new archetypes + Elowen + a shared Ravendale-lore quality-
push bank, all in one pass) regressed coherence rather than improving
it — agreement dropped 0.9771→0.9536, garbling spread beyond
Shadewrath/Korrath to previously-clean characters including Selena.
M11.1 exists to actually answer the question M11's combined retrain
made impossible to answer: does the lore-bank lever work at all, in
isolation? Per Luke's direction (2026-07-22), M11.1 also takes on two
larger, related pieces of unfinished business: fully unifying every
character onto the compositional scheme ("a fully genericized model"),
and adding real new expressive range via one carefully chosen new
conditioning axis, not a wishlist of them.

## Why these three belong in one milestone

They're not independent asks bundled for convenience — genericization
is what makes the isolated-retrain methodology *and* the new-axis
work actually clean:

- Isolating the lore-bank lever requires a real, controlled baseline.
  Doing that controlled comparison on the *current* mixed-scheme cast
  (compositional cast on one schema, Shadewrath/Korrath/Elowen/guard on
  the old `N:<id>` scheme) means the lore-bank fix only ever helps
  three isolated old-scheme characters — the smallest possible test of
  whether shared reinforcement works, when the whole point is that
  reinforcement scales with how many characters share a token space.
- Genericization is the thing that makes reinforcement possible at
  full strength: once Shadewrath/Korrath/Elowen/guard condition
  through the same `P:/D:/OCC:/R:/M:/C:/EV:` tokens the compositional
  cast already uses, *every* character sharing a descriptor or
  occupation reinforces every other one sharing it — the lore-bank
  splice becomes one instance of a mechanism that's already proven at
  scale (M9's whole thesis), not a bespoke three-character workaround.
- A new axis is safest to test on a freshly-unified scheme: adding
  `AUD:` to one legacy corpus module and not another would be exactly
  the kind of inconsistency that's caused real bugs this project
  already hit (M9/M10's "wrong conditioning axis" pattern). One
  schema, one place to add a new token, one retrain to prove it.

## Part 1 — full genericization: one scheme, not two

Migrate `selena`, `shadewrath`, `korrath`, `elowen`, and `guard` off
`ContextBuilder`'s old `N:<id> TR:<tier> M:<mood> C:<context>
EV:<event>|` scheme onto `NpcService::buildPromptFields()`'s
compositional scheme, the same one every M9/M10/M11 archetype already
uses. Concretely:

- Each of these five gets a real `NpcService::Profile` (occupation,
  age, gender, the 5 personality traits) instead of a bare `N:<id>`
  tag. Selena's `{90, 85, 70, 55, 30}` already exists and is exactly
  what M9's own calibration check was built against — this is
  formalizing something already true, not inventing new content for
  her specifically.
- `occupation` needs real values for Shadewrath (`"noble"`? a
  necromancer isn't cleanly any of the 12 existing `OCCUPATIONS` —
  this may need a 13th entry, e.g. `"villain"` or `"sorcerer"`, a real
  manifest-schema decision to make deliberately, not default past) and
  similarly for Korrath (`"guard"`? — thematically close but would
  merge his voice into the same occupation-flavor bank as the town
  guard archetype, which may or may not be wanted) and Elowen (no
  existing occupation fits "captive royalty" — likely needs its own
  entry too, e.g. `"noble"` already exists and fits her cleanly).
- `ContextBuilder.cpp` and the old `N:<id>` scheme itself: not deleted
  — `guard_corpus.py`'s existing shipped, hardware-verified corpus
  stays on it unless a real decision is made to retrain guard too (a
  second, larger question, same one M10's own manifest note already
  flagged and deferred: "migrating it would require retraining
  guard's existing, shipped, hardware-verified corpus, out of scope").
  Recommend genericizing Selena/Shadewrath/Korrath/Elowen first (the
  higher-leverage four, all currently isolated single-voice content)
  and leaving guard on the old scheme as a deliberate, recorded
  scope boundary for this pass — revisit only if the first four prove
  the migration is worth guard's own retrain cost too.
- Real work, not a relabeling: every existing corpus module for these
  four characters (`selena_corpus.py`, `shadewrath_corpus.py`,
  `korrath_corpus.py`, `princess_corpus.py`) currently generates
  prompts via `prompt_for()` on the old scheme. Each needs a
  `generate_pairs()` variant (or a full rewrite) emitting
  `prompt_fields()`-shaped strings instead — real trainer-side work,
  not a docs change.

## Part 2 — the isolated retrain

Once genericized, run the actual controlled experiment M11's own
combined retrain skipped:

1. **Baseline**: the genericized cast, *without* the Ravendale-lore
   bank, retrained fresh (val loss/agreement/divergence become the new
   reference point — the old N:-scheme baselines from M9-M11 don't
   transfer cleanly once the schema itself changed).
2. **Treatment**: the identical genericized cast, *with* the
   Ravendale-lore bank spliced in (now reinforcing across however many
   characters share its descriptor/occupation tokens, not just three
   isolated ones) — same seed, same everything else.
3. Compare using the same metric battery `docs/ideas-capacity-scaling-
   evaluation-plan.md` already specifies (val loss, agreement,
   divergence table with a numeric floor, invented-word count on a
   fixed golden set, error categorization) — that plan's whole
   methodology was written to prevent exactly the kind of ungrounded
   "seems better" call M11's retrain would have invited if agreement
   hadn't caught it. Reuse it here rather than re-deriving a second
   evaluation protocol.
4. Pre-register the acceptance bar *before* running the treatment, per
   the same discipline — what specific, numeric improvement counts as
   the lore-bank lever actually working this time.

## Part 3 — one new axis: `AUD:` (audience)

**Recommended, not yet decided — confirm before implementing.** Every
character's manifest bible already has `public`/`private`/`secret`
fields (`docs/08-manifest-schema.md`) that have existed since M7 as
pure authoring guidance — content a corpus author reads, never
something the model can act on directly. `AUD:` operationalizes it:

- Values: `alone` (player is the only audience — private-register
  content is fair game) / `witnessed` (other NPCs or the town present
  — public-register content only). A third tier (`AUD:trusted` — a
  close-relationship threshold unlocks private content even when
  technically witnessed) is a plausible v2, not required for v1.
- Corpus impact: each character's existing `_OPENERS`/`_BODIES`/
  `_CLOSERS` banks likely already sort naturally into public vs.
  private register (a look at Shadewrath's own bank shows this split
  is already latent — his `tender` mood openers are already more
  "private" in tone than his `sassy` ones) — this may be more of a
  *labeling* pass over existing content than all-new authoring, which
  keeps the corpus-volume cost low relative to the payoff.
- Alternative candidates considered and deliberately not chosen for
  this pass (see the brainstorm in the session that proposed this
  milestone): a relationship-*type* axis (`BOND:` — rival/mentor/
  family, orthogonal to R:'s closeness scale) and a species/ancestry
  axis (`SPECIES:`, thematically strong given Elowen's already-elf
  identity) are both real, recorded here for a future pass — not
  bundled into this one, on the same "one variable at a time" logic
  Part 2 already argues for.

## Definition of done

- [ ] Selena, Shadewrath, Korrath, Elowen genericized onto the
      compositional scheme; guard deliberately left on the old scheme,
      recorded as a scope boundary, not an oversight
- [ ] Baseline retrain (genericized cast, no lore bank) — real
      val loss/agreement/divergence numbers established
- [ ] Treatment retrain (genericized cast + lore bank) — same corpus
      otherwise, same seed
- [ ] Comparison run against `docs/ideas-capacity-scaling-evaluation-
      plan.md`'s metric battery, pre-registered bar, honest result
      either way
- [ ] `AUD:` axis added (or explicitly deferred with reasoning, if the
      isolated retrain's own result changes the priority call)
- [ ] Host tests + trainer tests green throughout
- [ ] ROM boots, SELFTEST PASS, RSP ON, XCHK PASS on real hardware
- [ ] Docs: this file finalized with real numbers, README status row,
      tag `m11.1`

## What M11.1 deliberately does not do

- Migrate `guard` onto the compositional scheme — deliberately
  deferred, see Part 1
- The H=768/ktile capacity-scaling experiment
  (`docs/ideas-capacity-scaling-evaluation-plan.md`) — a separate,
  larger effort with its own prerequisites (human sign-off on
  `core/ngpt.h`, kernel integration); this milestone's isolated retrain
  is what generates a cleaner baseline for that plan to measure against
  later, not a replacement for it
- `BOND:`/`SPECIES:` or any other brainstormed axis beyond `AUD:` —
  recorded as real candidates for a future pass, not this one
