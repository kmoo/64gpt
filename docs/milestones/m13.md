# M13 — LLM-assisted phrase-bank distillation (planning — not started)

**Status: PLANNED.** Claimed the M13 slot 2026-07-26 from the portability
release, which moves to `docs/milestones/m14.md` (see that file's
Renumbering note #3) — this milestone is the active next-in-sequence
work; portability remains dormant ("PLANNED, not started" since the
original M11→M12 split) with nothing currently blocking on it.

No hard code dependency on the M12.2-M12.5 voice-conditioning line (this
is a different kind of lever, see "Why" below), but sequencing-wise it's
cleaner to start once `m12.3-voices`'s fate (merge or park) is decided,
so this doesn't build on top of an unresolved experimental branch.

## This is NOT M9's `llm_judge.py` — a different, bigger mechanism

`trainer/llm_judge.py` (built and run once, M9, commit `24458f3`, never
touched since) is a **pure rater**: it scores already-generated corpus
lines 1-5 on coherence/voice and writes a report. It never rewrites
anything and never feeds anything back into a training corpus — closer
to a linter than a training mechanism.

What this milestone actually is — LLM-authored content entering the
training corpus, not just grading it — is a materially bigger step, and
one this project has a directly relevant, cautionary data point for
already (next section). The plumbing (batched dispatch, JSON prompt/
parse, `opencoder` routing) should still be **reused and extended**, not
duplicated — see "Build on, don't rebuild" below.

## M12.6's negative result sharpens mechanism 2

M12.6 (`docs/milestones/m12.6.md`) hand-expanded korrath/elowen's bank
density to match shadewrath's, using only existing vocabulary/motifs,
integrated through the same template grammar (not one-off lines). It
did not close the gap — elowen actually regressed (3.00 vs M12.4's
1.88) — independently supporting mechanism 2's premise below: raw
bank-entry count is not the lever, even when well-integrated. This
milestone's bet is specifically on fragment *quality/structural fit*
(judge-vetted, density-gated), not just *quantity*.

## Why — and a retargeting from the original pitch

The original conversation proposal framed this as fixing "free-running
generation quality... coherence... avoidance of gibberish." That framing
needs a correction: **M12.1 already gave the shipped model a hard
structural guarantee against invented words** (the lexicon-trie decode
guard — 0 invented words across all 36 shipped goldens, not a
probability, a structural impossibility). Generic gibberish-avoidance is
not this project's open problem anymore.

What IS still open, per M12.4's own findings: getting the model to
reliably express D:/M: attribute conditioning on **thin-corpus
characters** — guard (1.75 inv/line) and korrath (2.00) lag well behind
selena (0.62) and cast (1.12) on the raw (unguarded) coherence probe,
even with M12.4's best conditioning-mechanism result so far (1.44
overall, gate ≤1.00). This milestone's real value is a **corpus-quality**
lever aimed specifically at that gap — complementary to the
conditioning-*mechanism* work (M12.2-M12.5), not a replacement for it.

## The cautionary precedent this design must not repeat

M9's Attempt #1 (`docs/milestones/m9.md` §4, `generate_m9_corpus_llm.py`)
already tried "use an LLM to author corpus text" once. `llm_judge.py`
rated that corpus **4.75/5 coherence, 4.18/5 voice** — looked great in
isolation. The **model actually trained on it** produced garbled output
scoring **3.36/5 coherence, 2.64/5 voice**, with real invented words
("FORENTURESS", "CAVILY", "COMEEFILUTHING"). Root cause, confirmed
against the corpora that do train cleanly: freeform LLM text has high
lexical diversity and almost no repetition (~1,300 chars/persona);
Selena and guard train cleanly because they're deterministic
template-grammar generation with high controlled repetition (~120K+
chars/character). **This is the single most important fact this
milestone must design around** — a judge rating text as "good" tells you
nothing about whether a ~100-400K-param char-GRU can learn from it.

M9's own Data Science Review flagged "does the LLM-judge's score
correlate with human judgment / real model quality" as explicitly
unresolved. As far as this review can find, **no later milestone ever
answered that question.** It's not just historically interesting — it's
the exact premise this milestone's whole approach rests on, still
unvalidated after 9 milestones. See mechanism 4 below.

## Four mechanisms, each closing off one way this repeats M9's mistake

### 1. Intervene at the bank level, not the line level

Don't judge/rewrite whole assembled lines and insert them as one-off
replacements — that's Attempt #1 with extra steps. Instead, have the LLM
propose new **bank fragments** for guard/korrath's existing
descriptor/context/tier banks (`guard_corpus.py`, `korrath_corpus.py`):
openers, body-skeleton templates, catchphrase entries — the same
ingredient categories M9's Attempt #2 already proved work
(`docs/milestones/m9.md` §4). Each accepted fragment gets woven through
the *existing* template-grammar generator and reused across dozens of
combos automatically, inheriting the repetition structure that already
trains cleanly, instead of being judged as an isolated sentence.

### 2. Make the density lesson an enforced, quantitative gate

M9's finding ("~120K+ chars/character, not ~1,300") becomes a literal
check, not a prompt instruction to hope the LLM respects: any new
bank fragment only survives if, once folded into the corpus generator,
it gets reused **≥K times** across distinct generated combos (K TBD
empirically, calibrated against guard/cast's own proven density). A
fragment used once is exactly Attempt #1's failure mode in miniature.

### 3. Split what the LLM is good at from what it isn't

A big LLM has no notion of what makes a tiny char-GRU trainable — that's
precisely why 4.75/5-rated text produced a 3.36/5 model. Run a cheap,
**programmatic structural-compatibility gate before any LLM call**:
reuse `ngpt_trainer.divergence.jaccard_distance` (already used for
near-duplicate detection in `llm_judge.py`) and `build_corpus_vocab`/
`invented_word_count` (`make_m12_1_blob.py`) to reject fragments with the
wrong repetition/density/vocabulary signature for free, before spending
any tokens. Only pay for LLM judgment on tone/voice plausibility — the
part it's actually good at — for candidates that already clear the
structural bar.

### 4. Actually close M9's open validation question, using M11.1's playbook

Before trusting judge-driven corpus changes for real: **pre-register a
bar before either result is seen** (M11.1's own discipline,
`docs/milestones/m11.1.md` Part 2 — the project's most rigorous
precedent for exactly this kind of "does the metric predict the real
outcome" question). Generate a handful of judge-approved and
judge-rejected bank-fragment sets, actually train quick models on each
(cheap at this project's scale — tiny-corpus overfit training already
runs in seconds), and check whether judge score predicts the real
downstream coherence-probe number. If it doesn't correlate, that's the
answer, and it's learned *before* building the rest of the pipeline on
top of an unvalidated premise — not after, the way M9 discovered its gap
by accident partway through.

### Mechanism 4's protocol, locked 2026-07-27 before any result was seen

Drafted with Luke, revised once after a data-science-style critique of
the first draft caught three real design flaws before they could bias
the result: (1) an uneven approved/rejected split size would confound
"judge quality" with "M12.6-proven quantity/density effects"; (2) a
single run per arm has no noise floor to compare against; (3) the
original pass bar (fixed percentage margins) was arbitrary, not
calibrated to anything. Fixed below.

**Scope:** guard and korrath only -- M12.4's two laggards (1.75 / 2.00
inv/line vs the <=1.00 gate).

**Steps:**
1. Generate candidate OPENER-style fragments for guard/korrath via one
   straightforward `opencoder` dispatch -- no deliberately-injected
   good/bad mix, to avoid biasing the split toward an easy result.
2. Run every candidate through the structural gate (mechanism 3,
   `corpus_gates.py`, already shipped).
3. Judge survivors 1-5 on tone/voice-plausibility, extending
   `llm_judge.py`'s dispatch/parse machinery with a new rubric (the
   D:/M: attribute values in play have to be part of the prompt, per
   mechanism 3's own note -- "fidelity to tone" is meaningless without
   knowing which voice archetype is judged).
4. Rank survivors by score. Take the **top-K as approved, bottom-K as
   rejected -- equal K** on both sides, fixing the quantity confound.
5. **Human spot-check (Luke) of the approved/rejected split, required
   before any training compute is spent** -- same discipline
   `llm_judge.py` already applies to whole lines (M9's Data Science
   Review), never previously extended to fragment-level judging.
6. Four full-cast retrains (guard/korrath share one model with the rest
   of the cast per M11.1's compositional design -- there's no isolated
   "just guard/korrath" run), same probe methodology as
   `trainer/m12_4_attr_ablation_spike.py`:
   - baseline, seed A
   - baseline, seed B (same corpus, different seed -- this run's ONLY
     purpose is measuring the noise floor)
   - baseline + approved-K fragments
   - baseline + rejected-K fragments
7. Measure invented/line for guard+korrath (and each individually) on
   all four runs.

**Pre-registered bar (self-calibrating, not a fixed percentage):**

```
noise_floor = |baseline_seedA - baseline_seedB|   (invented/line, guard+korrath)

PASS  if  approved <= baseline + noise_floor
      AND (rejected - approved) > noise_floor

INCONCLUSIVE  if the approved/rejected gap is within noise_floor of the
              cutoff -- reported as its own honest outcome, not forced
              into PASS or FAIL

FAIL  otherwise
```

PASS means the judge's tone/voice score predicts real training impact
well enough to trust for mechanism 1's real pipeline. FAIL or
INCONCLUSIVE means it doesn't (at this K, this rubric, this corpus) --
a valid stopping point for the LLM-authoring half of this milestone,
same discipline as every other honest negative this project has
recorded. Note what this bar does NOT claim: even a clean PASS only
means the judge is directionally trustworthy, not that this path can
reach the real <=1.00 target -- that's a separate, later question.

## Pipeline (v1 scope)

1. **Candidate generation.** LLM proposes new opener/body-
   skeleton/catchphrase fragments for guard/korrath's existing bank
   categories (mechanism 1) — not whole free-running lines.
2. **Structural gate (free, before any further LLM spend).** Reject
   fragments with wrong vocab/repetition signature (mechanism 3).
3. **Judge pass on survivors.** Batched, extends `llm_judge.py`'s
   existing dispatch/JSON-parse/`opencoder`-routing machinery (not a new
   client) with a tone/voice-plausibility rubric that includes the D:/M:
   attribute values being targeted — "fidelity to tone" is meaningless
   without knowing which voice archetype is in play.
4. **Density gate.** Fold accepted fragments into the generator, require
   ≥K-combo reuse before they're kept (mechanism 2).
5. **Validation experiment (mechanism 4), once, before trusting this for
   real.** Pre-registered judge-score-vs-real-outcome check.
6. **Train/QAT/verify.** Ordinary next-character cross-entropy + the
   existing QAT recipe, same fixed seeds/snapshot discipline as every
   other milestone. Re-run the raw (unguarded) coherence probe against
   M12.4/M12.5's numbers, specifically on guard/korrath, plus the full
   self-test/XCHK suite. **The probe number is the only signal that
   counts** — not the judge score, per the cautionary precedent above.

## Explicitly cut from v1 scope

- **DPO / preference-pair fine-tuning.** No ranking/DPO training
  infrastructure exists in this codebase today. Park as an M13.1 idea
  only if the bank-distillation path alone doesn't close enough of the
  guard/korrath gap.
- **Line-level judge+rewrite of whole free-running generations** (the
  original pitch's core mechanism) — superseded by mechanism 1 above for
  the reason M9 already demonstrated.

## Practical notes specific to this repo

- **Build on, don't rebuild:** extend `trainer/llm_judge.py`'s existing
  dispatch/parse/routing rather than writing a new batched LLM client.
- **Local-model routing:** `~/bin/opencoder` (`OPENCODER_TYPE=text`,
  Mistral-7B), same as `llm_judge.py` already uses — not a new Qwen3.5
  dependency. Run the memory-audit ritual before any large batch.
- **Claude API calls are a new kind of dependency for this project** if
  used for escalation — real API key, real billing, network dependency
  in the trainer pipeline. A deliberate go/no-go decision, not something
  to wire in quietly.
- Pure trainer/corpus-side work — no `core/`, blob format, or N64 kernel
  changes.

## What this milestone deliberately does not do

- Does not re-solve gibberish/coherence in general — M12.1's trie guard
  already makes that structurally impossible in the shipped ROM
- Does not judge/rewrite whole free-running lines for direct corpus
  insertion — mechanism 1 explains why, grounded in M9's own measured
  failure
- Does not include DPO/preference-pair training
- Does not touch `core/`, the blob format, or the N64 kernel
- Does not replace the conditioning-mechanism work (M12.2-M12.5) — it's
  a corpus-quality lever that stacks with whichever mechanism wins
- Does not trust the LLM-judge score as a gate on its own — the
  coherence probe (real trained-model output) is the only thing that
  decides success, per the 4.75/4.18-vs-3.36/2.64 precedent
