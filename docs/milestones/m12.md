# M12 — Capacity scaling: does a bigger model fix coherence? (DONE — honest negative)

**Status: DONE (2026-07-23).** Depends on M11.1 (`docs/milestones/
m11.1.md`), which shipped the clean H=320 baseline this experiment needed
and ruled out both of the project's previously-identified content-side
coherence levers (raw pair count, shared structural content). This
milestone tests the one remaining hypothesis on record
(`docs/plan.md`'s Known follow-ups): "accept this needs more model
capacity than a corpus change alone can buy." Answers the question
`docs/ideas-capacity-scaling-evaluation-plan.md` posed and the
`spike/rsp-matvec-ktile` branch's own handoff named directly: "whether a
real model at whatever H gets chosen, trained on real corpus, produces
better dialogue — not just correct/fast inference — is completely
untested. [The spike] proved the kernel, not the model."

that `docs/ideas-capacity-scaling-evaluation-plan.md` itself anticipated

## Why

M11.1 closed off two of three identified coherence levers cleanly
(`docs/plan.md` Known follow-ups: raw pair count tried at M10, shared
structural content tried and isolated at M11.1, both insufficient). The
third — more model capacity — had real, hardware-verified groundwork
already sitting on `spike/rsp-matvec-ktile`: a K-chunked RSP kernel
proven correct at H up to 1024 (9/9 bit-exact XCHK passes), but never
trained on a real corpus or evaluated for text quality. This milestone
closes that gap: train the real M11.1 corpus at H=1024, same seed, same
everything else, and see whether capacity was ever the actual
bottleneck.

## What shipped

### Part 1 — porting the kernel onto current `main`

The ktile spike diverged from `main` all the way back at M9 and never
merged — `docs/spikes/rsp-matvec-ktile.md`'s own handoff explicitly
warned against reviving it wholesale ("integrating the K-tiled kernel
means merging into current main, not reviving a stale branch"). Instead
of a git merge/rebase across that much drift, the K-chunked technique
was ported by hand onto current `main`'s actual files:

- **`core/ngpt.h`**: `NGPT_GRU_MAX_HIDDEN` bumped 320→1024, with
  explicit human sign-off (Luke, 2026-07-23) — `core/` is a frozen
  interface per this project's own hard constraints, and this decision
  was treated as a deliberate, called-out step, not a merge artifact.
  H=1024 over the spike's own recommended H=768 was a deliberate
  "how far can this actually go" choice, accepted with eyes open to the
  real cost (see Part 2).
- **`game/src/user/rsp_ngpt.S`**: replaced with the K-chunked kernel
  (`NgptMatvec`/`DotRowChunk`), ported from the spike's exact
  hardware-verified H=1024/CHUNK=256 configuration (commit `bc3a2c9`).
  2D-tiled — 384 row-tiles × 4 K-chunks — DMEM footprint 3104B `.bss`,
  structurally independent of H (the whole point of K-tiling: it
  decouples DMEM from H, unlike every prior kernel back to M6.1's
  original design).
- **`game/src/user/DialogueDemo.cpp`**: `RSP_H` bumped to 1024; buffer
  sizes scale automatically off that constant (`rspWhh` 3MB, up from
  300KB at H=320 — RDRAM, not DMEM, is the real constraint at this H).
- **`core/ngpt_gru.cpp`**: the CPU reference path's row-sum and bias-add
  widened to int64 internally, saturating on narrow-back to int32. This
  does NOT protect the RSP hardware path itself (real cycles on
  hardware with no native 64-bit op, not a free fix) — it protects the
  *reference* the boot self-test's CPU-vs-RSP cross-check treats as
  ground truth, so if the RSP path's own unwidened int32 accumulator
  ever does overflow on real trained weights, it diverges from a now-
  correct reference instead of both paths silently wrapping the same
  way and still agreeing. Verified with a new host test,
  `tests/test_overflow_mitigation.cpp` (fills `acc_h` with fixed
  near-`INT32_MAX`/`INT32_MIN` values via the existing `ngpt_set_matvec`
  hook mechanism, confirms generation completes without propagating UB
  into the sampler).
- **Async double-buffered DMA** (the ktile spike's own "real lever,
  still unclaimed by any version of this kernel") — considered,
  deliberately not attempted. Requires restructuring the DMEM tile
  budget itself (shrinking `TILE_ROWS` for ping-pong buffers) with an
  explicitly unmeasured payoff, on top of an already-verified, already-
  at-target kernel. Recorded in `docs/plan.md` Known follow-ups as real,
  deferred work, not a quiet drop.

Host suite: 11/11 green (10 prior + the new overflow test).

### Part 2 — training and MPS

Trained via `trainer/make_m12_blob.py` on M11.1's exact shipped corpus
and seed (genericized cast, lore bank off — the Part 2 winner), only
`HIDDEN` changed. Training used `device="mps"`, not the `"cpu"` every
prior `make_mN_blob.py` forced — H=1024's ~10.24x more `W_hh` parameters
than H=320 (quadratic in H) made the CPU-only rule genuinely costly here
in a way it wasn't for any smaller prior model. Luke's own updated
`CLAUDE.md` policy (2026-07-23) allows this once opencoder's MLX server
is confirmed down right before the run — checked (`opencoder status` →
`DOWN`) before launching.

**Real-world footnote, not swept under the rug:** the first two launch
attempts hit operational snags unrelated to the model itself — a `uv`
cache lock left stuck by an earlier aborted run (fixed by clearing
`~/.cache/uv/.lock` and relaunching), and an orphaned duplicate training
process left running after a `kill` only took out its parent (both
processes were burning real CPU concurrently until caught and killed).
Neither affected the final result; recorded because "the training run
itself was clean" would be a less honest account of how this session
actually went.

### Part 3 — a real bug found and fixed along the way

The first hardware boot came back **SELFTEST FAIL** with **XCHK PASS**
— a specific, informative failure pattern (CPU and RSP agree with each
other, but the on-device generation doesn't match the pre-recorded
goldens). Initial hypothesis was the disclosed int32-overflow risk
actually materializing on real trained weights. Verified instead of
assumed: a host-side diagnostic replayed all 36 goldens through the
CPU-only (int64-protected) path and found 3 mismatches, each showing
the *same* text as the recorded golden up to **exactly 256 characters**,
with the live device naturally continuing a few more words to its real
EOS.

Root cause: `ref_impl.py`'s `generate_sampled()` defaults `max_len=256`,
and none of `make_m9_blob.py` through `make_m12_blob.py` ever passed
this milestone's own `MAX_GOLDEN_LEN=300` through to it — every golden
was silently capped at 256 regardless of the constant that was supposed
to govern it. **This was not a new M12 bug** — the same gap exists in
`make_m11_1_blob.py` and earlier, just never manifested as a visible
SELFTEST failure before, because H=320's shorter, more coherent
generations rarely ran past 256 characters. H=1024's longer, more
rambling output exposed a latent pipeline bug that had nothing to do
with capacity, overflow, or the RSP kernel port. Fixed by threading
`max_len=MAX_GOLDEN_LEN` through all 4 `generate_sampled()` call sites
in `make_m12_blob.py`; the same fix should be back-ported to
`make_m11_1_blob.py` and earlier scripts as a follow-up (M11.1's actual
shipped goldens happened not to trigger it, so nothing shipped is wrong
— but the risk was real and latent there too).

## Result: honest negative

| metric | M11.1 (H=320) | M12 (H=1024) |
|---|---|---|
| val loss | 0.1015 | **0.1051 — worse** |
| int8-vs-float agreement | 0.9508 | 0.9696 |
| invented words / golden (probe) | ~2.65 (69/26) | ~2.47 (91/36) |
| divergence: occupation | 0.9355 | 0.8936 |
| divergence: mood | 0.9127 | 0.9127 |
| divergence: trust | — | 0.9128 |
| divergence: context | — | 0.9345 |
| speed (RSP) | 44 ch/s | ~5 ch/s |

**10x more capacity did not fix the coherence problem.** Val loss
landed *worse* than the H=320 baseline it was supposed to beat, not
just short of the pre-registered "beat the all-time low" bar (0.0980,
M10 v1). Agreement improved and divergence stayed structurally healthy
(no collapse), but the actual target — garbled, invented-word text —
didn't move: reading the golden probe, H=1024's output is just as
garbled as H=320's, arguably with some worse individual examples ("THE
GOBLIN WEICH ONE NO," "I FEAR I HAVE FORGOT WORSE," 7-9 invented words
in single goldens).

This is the third coherence lever this project has tried and found
insufficient (after raw pair count at M10 and shared structural content
at M11.1), and the first to test the *other* half of `docs/plan.md`'s
own standing hypothesis ("share more structural content... or accept
this needs more model capacity than a corpus change alone can buy").
Both halves are now tested. Neither fixed it. This argues the
coherence gap is not primarily a capacity-starvation or corpus-
authoring problem — something else (architecture, training procedure,
decoding strategy, or a more fundamental data/task mismatch) is more
likely the real bottleneck. See `docs/plan.md` Known follow-ups for the
full standing record and what's left untried.

**Speed accepted as a known tradeoff, not a regression nobody signed
off on.** ~5 ch/s is well under M5's shipped ≥30 ch/s bar and even
under the spike's own recommended H=768 (9.49 ch/s) — an explicit,
deliberate choice (H=1024 over H=768, "how far can this go" over "what's
defensible") made with the real cost disclosed in advance, not
discovered after the fact.

## Hardware verification

ROM v1.8 rebuilt with the corrected goldens, booted clean in Ares:
**SELFTEST PASS, RSP ON, XCHK PASS** for all 36 goldens, ~5 ch/s,
`CPU 687782us RSP 194522us` per step at boot. The K-chunked kernel port
itself is proven correct on real (emulated) hardware — the quality
result is a negative on the *model*, not a failure of the *engine
work*.
