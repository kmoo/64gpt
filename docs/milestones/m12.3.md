# M12.3 — Per-step D:/M: attribute conditioning: a second honest negative

**Status: LANDED (2026-07-26) as a code/test commit — NOT a ROM/model
release.** What shipped: the attribute-conditioning mechanism itself
(tested, working, reusable) and this finding. What did NOT ship: a
model that clears the coherence gate — this spike's result is worse
than M12.2's own failing baseline. Depends on M12.2
(`docs/milestones/m12.2.md`) and `docs/ideas-m12.3-conditioning-
strategies.md` (option A).

## What we tried

Option A from the conditioning-strategies doc: give the D: (voice
descriptor) and M: (mood) fields a per-step presence that can't decay
across a long reply, instead of relying on the text prefix alone. A
learned embedding concatenated onto the char input at every timestep is
mathematically identical to appending more one-hot columns that share
the *same* `weight_ih_l0` matrix (an `nn.Embedding` lookup **is** a
one-hot-times-weight-matrix select) — so the implementation reused
`CharGRU`/`quantize()`/`qat_finetune`'s existing machinery almost
unchanged rather than adding a new module:

- `npc_service.parse_prompt_fields()` — generic colon-token parser,
  recovers D:/M: (or any field) from the existing prompt string. Zero
  corpus generator files touched.
- `model.CharGRU(..., input_size=vocab_size + n_desc + n_mood)` —
  `input_size` decoupled from `vocab_size` (previously always equal).
  `model.one_hot_attr()` builds the widened one-hot: char columns +
  two **constant** attribute columns, held "on" for every timestep of
  the whole sequence (prompt and response) — an NPC's voice/mood is
  fixed for one reply.
- `model.train_corpus_conditioned_attr()` / `qat_finetune_attr()` —
  same training-loop shape as the M7/M12.1 originals, batching the wider
  input.
- `ref_impl.gru_h_update(q, h, x_id, attr_cols=())` — the exact same
  column-lookup trick already used for the char id, extended with more
  columns. Opt-in, byte-exact when `attr_cols=()` (same convention as
  `sample_from_logits`'s `minp_shift`). `ref_impl.prime_attr` /
  `gru_step_attr` / `generate_sampled_attr` thread it through priming
  and generation.
- The text prefix (`P:/D:/OCC:/.../M:/C:/.../EV:`) was left **unchanged**
  — this was additive ("keep both"), the safer of the two options the
  design doc left open, not a replacement.

**Validated before the real run:** `trainer/tests/test_m12_3_attr.py`
overfits a tiny corpus where the ONLY signal distinguishing two groups
of examples is the attribute id (identical prompt text, different D:
id) and confirms the trained + int8-quantized model reproduces the
correct response for each id — proof the mechanism reaches the output
and survives quantization, before spending real training time on it.
204 pytest passing (`trainer/`), no regressions.

## The honest negative

`trainer/m12_3_attr_spike.py` (host-only: fp32 train + int8
`quantize()`/`ref_impl`, no blob/kernel/ROM artifacts) trained H=320 on
the `m12.3-voices` branch's richer corpus (9 D: values, 5 M: values,
~59K pairs, same build config as M12.1's `make_m12_1_blob.py`) and ran
the exact M12.1/M12.2 coherence-probe methodology (quantized, no trie,
same seeds/settings) against it:

| | invented/line |
|---|---|
| M12.1 gate (target) | ≤ 1.00 |
| M12.2 baseline (prefix-only, no attr conditioning) | 1.65 |
| **M12.3 (D:/M: attribute conditioning)** | **2.33** |

Worse across every character group (selena 2.50, guard 2.12, cast 1.62,
shadewrath 3.00, korrath 2.25, elowen 2.50), not a single outlier.
**Decision gate: does not clear ≤1.0, does not even beat 1.65 — per the
design doc's own sequencing, this means no blob/kernel work.**

Training itself was also visibly less stable than M12.1/M12.2's runs:
the float phase needed 54 epochs (vs. fewer for M12.1) with several
2-8x val-loss spikes recovering the next epoch, and QAT — which
*improved* val loss in M12.1 (0.1141→0.1002) — got monotonically
*worse* every epoch here (0.1966→0.2521) until its own patience
triggered and restored epoch 0's weights.

**Root-cause investigation, live:** the first hypothesis (attribute
columns grow outsized weight magnitude, forcing a coarser shared int8
quantization scale `k_w` that degrades every column including the char
ones) was checked directly against the trained float weights and
**falsified** — char columns are the *larger*-magnitude ones (max
`8.03`) vs. desc (`3.89`) and mood (`1.07`). Ruled out, not just
unconfirmed.

The more likely explanation, **not yet confirmed**: D:/M: are already
present in the text prefix, so the attribute columns are a **redundant**
signal, not new information — but they DO create a structural asymmetry
during training, since they get gradient contributions from *every*
timestep of a 200+ character unroll (prompt + response), unlike a char
column which only fires at its few actual occurrences. That asymmetry
is a plausible fit for the training instability observed, but this is a
hypothesis to test, not a proven cause.

## What DID land (unambiguous, corpus-independent)

- The attribute-conditioning mechanism itself: `parse_prompt_fields`,
  `CharGRU`'s decoupled `input_size`, `one_hot_attr`,
  `train_corpus_conditioned_attr`, `qat_finetune_attr`,
  `ref_impl.gru_h_update`'s `attr_cols` parameter and its priming/
  generation wrappers — all tested, all reusable for the next attempt
  (M12.4/M12.5, see below), independent of whether THIS spike's specific
  application of them worked.
- The magnitude-hypothesis falsification (saves a future session from
  re-checking it).
- `trainer` pytest green (204 passed, 3 deselected slow); no C++ files
  touched this session, `core/` unaffected.

## For M12.4 / M12.5

Two candidate follow-ups, both real multi-hour retrains, not yet run:

1. **Redundancy ablation (recommended next, cheaper to build):** retrain
   with D:/M: stripped from the text prefix, so the attribute columns
   are the *only* source of that signal — isolates whether redundancy
   itself is the regression's cause. If this clears the gate, it's a
   much smaller/cheaper fix than option B and may rescue the plain
   concat approach.
2. **FiLM (option B, docs/ideas-m12.3-conditioning-strategies.md):** if
   (1) is inconclusive or still fails, per-channel scale/shift
   modulation of the hidden state is the design doc's own next
   candidate — structurally avoids the every-timestep-gradient
   asymmetry redundancy ablation is testing for, at the cost of a real
   kernel-shape change (multiply-and-add per channel, not just an
   additive column lookup).

Sequencing recommendation: run (1) before (2) — it reuses this
session's code unchanged (only what's fed as the prefix text changes),
and is diagnostic regardless of outcome.
