# M6.1 — RSP-powered inference (ROM v1.1 for EverDrive testing)

**Status: NOT STARTED — this is the brief for the session that builds
it.** Goal: the demo ROM's GRU inference runs its hot matvec on the
RSP, **bit-exact** (the existing M4 goldens must still SELFTEST PASS),
measurably faster on the perf overlay, packaged for Luke's EverDrive.

Read first, in order: this file → `docs/spikes/rsp-matvec.md` (the
proven kernel + five-bug ledger) → branch `spike/rsp-matvec`, files
`game/src/user/rsp_ngpt.S` + `game/src/user/DialogueDemo.cpp` (spike

`docs/spikes/rsp-adoption-notes.md`.

## Why (the north star — from Luke, verbatim intent)

Speed is not the point; **headroom is**. This milestone exists so the
console can support a *better neural network* — the M7 vision's
500–800K-param "magic zone" (docs/ideas-m7-living-npcs.md) with the CPU
freed for world simulation. Build the RSP path so it scales: dims come
from the blob, tiling handles H=256 (rows of 256 int8 = two DMEM quads
per row-chunk), and nothing hard-codes H=128 except the engine's
`NGPT_GRU_MAX_HIDDEN` cap — raising that cap (128 → 256) and growing
ctx/scratch accordingly is IN scope if it stays green; training the
bigger model itself is the milestone after. Judge every design choice
by "does this still work at H=256 / ~500K params?"

## What the spike already proved (do not re-derive)

The full 384×128 int8×int16 matvec runs on the RSP bit-exactly at 2.8×
CPU speed (3,022µs vs 8,596µs, unoptimized). The kernel, its exactness
scheme, and the tiled-DMA structure are working code on the spike
branch. This milestone is *adoption engineering*, not research.

## Architecture (decided — matches the approved ngpt_set_sampler pattern)

- `core/` stays flat, `.cpp`-only, **libdragon-free**. The engine gains
  one additive hook (the frozen 4-call streaming API is untouched):
  a matvec callback the game can register; NULL (the default) keeps the
  pure-CPU path, so the host test suite runs unchanged and stays the
  bit-exactness referee. Suggested shape (lead may refine):
  `typedef void (*ngpt_matvec_fn)(const uint8_t *w_rows, uint32_t rows,
  uint32_t cols, const int16_t *h, int32_t *out);`
  `void ngpt_set_matvec(ngpt_matvec_fn fn);`
  The CPU adds the biases (cheap, 3H int32 adds) and does everything
  else; the callback computes only raw row·h sums.
- All RSP code lives game-side (`game/src/user/rsp_ngpt.S` + a thin C
  bridge). Lift files from the spike branch — **cherry-pick/copy, do
  not merge the branch** (it carries spike-only debug scaffolding).
- Scope: offload the W_hh 3H×H matvec (≈80% of MACs). W_ih is a column
  lookup (leave). Logits V×H offload and trainer-pre-shuffled weights
  are STRETCH, only after the base gate is green.

## Known traps — each cost the spike a debug cycle (full ledger in the report)

1. **Blocking on the RSP during `initDelete` hung the boot** with a
   black screen. The boot self-test generates text, so with the RSP
   path registered it will block in init → likely the same hang. Plan
   for it: run the self-test from the first update() frames (scene up,
   verdict visible), or register the RSP path only after the self-test.
2. **W_hh in the blob is not 8-aligned.** DMA from unaligned RDRAM
   shifts the DMEM landing address. Make one aligned(16) static copy of
   W_hh at load time (48KB, game-side) and DMA tiles from that.
3. **h must be even/odd shuffled once per step** (CPU-side, ~128 moves)
   to match the kernel's lqv byte-pair unpack.
4. **Every CPU/RSP-shared buffer owns its cache lines**: aligned(16),
   size a multiple of 16, one side uncached — or eviction writes stale
   bytes over DMA results (the spike's nastiest bug).
5. Vector shifts clobber the ACC; `lpv` rotates lanes by addr&15 — the
   shipped kernel already avoids both; don't "simplify" it back in.
