# M6.1 — RSP-powered inference (ROM v1.1) — DONE

**Status: DONE.** The demo ROM's GRU inference runs its hot matvec on
the RSP (the graphics coprocessor), bit-exact — the M4 goldens replay
byte-identically through the RSP path at every boot — at **4.8ms/char
vs 10.3ms all-CPU (2.1×)**, with the demo streaming at a held 60 VPS.
Shipped as `versions/m6_1_64gpt.z64` for EverDrive testing (hardware
run itself is M6, per `docs/hardware-checklist.md`).

Background reading order: `docs/spikes/rsp-matvec.md` (the proven
kernel + five-bug ledger) → this file → the M6.1 addendum in
`docs/07-performance.md`.

## Why (the north star — unchanged)

Speed is not the point; **headroom is**. This milestone exists so the
console can carry a *better 64GPT* — the generative language model we
built, scaled up: today's ~68K params (H=128) produce charming but
template-bound lines; the RSP's compute budget is what makes a
250K–800K-param generative model (H=256+, richer vocabulary, longer
coherence, real linguistic surprise) viable at playable speed — the
"magic zone" the M7 notes identify, with the CPU also freed for world
simulation on top. Every design choice below was judged by "does this
still work at H=256 / ~500K params?"

## What was built

**Core (`core/`, still flat, libdragon-free, host-testable):**

- `ngpt_set_matvec(fn)` — one additive hook; the frozen 4-call
  streaming API is untouched. A registered callback computes the raw
  row·h int32 sums for the W_hh matvec (rows/cols come from the blob —
  nothing hard-codes H); the engine adds biases and does everything
  else, so both paths produce bit-identical accumulators. NULL (the
  default) keeps the pure-CPU path: the host suite runs it unchanged
  and stays the bit-exactness referee.
- `tests/test_matvec_hook.cpp` proves the contract host-side: the hook
  is really on the hot path (a deliberately wrong callback changes the
  output), every M4 golden replays byte-identically through a correct
  callback, and NULL restores the default exactly.
- `NGPT_GRU_MAX_HIDDEN` raised 128 → 256: the engine now *accepts* the
  M7-scale blob. The int32 hot-loop bound still holds (a row sum is at
  most 256·127·32767 < 2^30; sum + bias fits int32) — revalidate
  against ref_impl when the H=256 blob actually ships.

**Game side (all RSP code stays out of `core/`):**

- `game/src/user/rsp_ngpt.S` — the spike kernel, adopted: `DotRow` and
  `NgptMatvec` verbatim (proven exact), spike bring-up scaffolding
  (echo/dot commands, debug dump) removed; one rspq command. Hooked
  into the build by the one-line ELF rule in `game/Makefile.custom`
  (n64.mk auto-assembles any `rsp*.S` — the filename prefix matters).
- A small bridge in `DialogueDemo.cpp` registers the backend via
  `ngpt_set_matvec`: W_hh is copied once at init into an aligned(16)
  static (48KB) because the blob offset is not 8-aligned and DMA from
  an unaligned RDRAM source lands shifted in DMEM; h is even/odd
  pre-shuffled per step (~128 moves) to match the kernel's lqv
  byte-pair unpack; every CPU/RSP-shared buffer owns its cache lines
  (aligned(16), 16-multiple size, CPU side uncached). Shapes the
  kernel can't take (anything but 384×128 rows over the registered
  W_hh) fall back to the exact CPU loop — that check is the H=256
  forward-compatibility seam until the ucode learns to tile wider rows.
- **The boot self-test moved out of `initDelete` and onto the screen.**
  Blocking on the RSP before the first frame hangs the boot (spike bug
  #1), so the self-test now runs from the first update() frames as a
  visible sequence: CPU reference generation → the same pinned-seed
  generation through the RSP with bytes *and* final hidden state
  compared (`XCHK PASS` on screen, belt and suspenders) → all 12 M4
  goldens replayed through the RSP path, one per frame with progress
  shown. Side effect: the ~10s black-screen boot of the m4/m5 ROMs is
  gone — the scene is up in ~1s.

## The numbers (Ares, first boot of the adopted path)

| | µs/char | raw ch/s |
|---|---|---|
| CPU path (measured at boot, same build) | 10,303 | ~97 |
| RSP path (matvec on RSP, rest on CPU) | **4,809** | **~208** |

On-screen perf line: `RSP ON XCHK PASS  CPU 10303 RSP 4776 US` (the
pair varies ±1% run to run); live streaming EMA ~5.3ms/char (the EMA
also averages the cheaper prompt-priming steps); 59–61 VPS while
streaming. Matches the brief's 4–6ms prediction: the kernel replaces
~8.6ms of CPU MACs with ~3.0ms of RSP time and the rest of the step is
unchanged. Known further headroom (pre-shuffled weights in the blob,
double-buffered tile DMA, 5×+ realistic) deliberately untouched — see
the spike report.

## Gotchas (new knowledge only — the spike ledger held)

- **The five spike traps were all real and all sufficient.** Planning
  around them (self-test out of initDelete, aligned W_hh copy, h
  shuffle, cache-line-owning buffers, kernel untouched) produced a
  first-boot-green adoption — zero new debug cycles. The ledger
  discipline paid for itself.
- `rspq_wait()` per character (~60/s sustained) coexists fine with the
  engine's own RSP use (graphics) — rspq interleaves overlays; VPS held
  at 60 throughout.
- The EOS step does a full h-update too, so per-step averages must
  count it (`steps+1`) or the CPU/RSP numbers skew ~1%.

## What M6.1 deliberately did NOT do (the next milestones' work)

- Train/ship the H=256 generative model (the whole point of the
  headroom) — needs trainer work, new goldens, ref_impl range
  revalidation, and a DotRow generalized past 128 columns (loop counts
  + stream offsets from a DMEM header, or per-H code — see the scaling
  note in `rsp_ngpt.S`).
- Logits (V×H) offload and trainer-pre-shuffled weights — stretch
  perf, only worth it once a bigger model needs the 5×.
- Double-buffered tile DMA / RowLoop unrolling — same.
