# M10 — Procedural cast: bosses, the villain, and dungeon-generated NPCs (planning — not started)

**Status: PLANNED.** Depends on M8 (archetype/instance system, proven
on `guard`) and **M9** (compositional conditioning — this milestone's
tiers ride on M9's feature-tuple mechanism, not M8's opaque per-id tags;
renumbered from the original M9 slot on 2026-07-17 when compositional
conditioning became M9 itself — see `docs/milestones/m9.md`). This is
where the dungeon crawler's other two cast categories get built: the
recurring named villain and the handful of talking bosses (persistent,
authored-ish, appear across the whole game), and the NPCs a
procedurally-generated dungeon level spawns on the fly (ephemeral,
seeded, no hand authoring per instance).

## Why

Town NPCs are static and hand-placed — M8's archetype system covers
them completely. Dungeon levels are generated "based on rules" per the
game design, and if an archetype instance can appear in a generated
level, its identity, personality jitter, and any placement logic need to
come from the *same* seed the level generator used, or the two systems
drift out of sync in ways that are hard to debug and impossible to
reproduce from a bug report. Meanwhile the villain and bosses are a
categorically different kind of character — they persist across many
separate encounters over a long play session, which is a form of
"continuity of existence" M7 and M8 never actually tested (Selena is
continuous within one town scene; archetype guards don't need memory at
all).

## Engineering plan — with the engineer hat on

### 1. A three-tier cast system, made explicit

The project has, without quite naming it, been building toward a
spectrum rather than a binary (full model vs. shared model) — M10 is
where that spectrum gets a name and concrete rules, because the
dungeon crawler's roster actually needs all three tiers at once:

| Tier | Who | Corpus | Memory |
|---|---|---|---|
| **Full** | Selena, the bad guy | full dedicated corpus (M7-scale, ~10MB) | persistent, long-horizon |
| **Mid** | talking bosses, a few named town figures (pub owner) | archetype-plus, more than a bare instance, less than full | persistent within their own arc |
| **Thin** | generic guards/wizards/damsels/shop patrons | archetype instance (M8), now composed from M9's feature vocabulary | none beyond the current encounter, or none at all |

**Tier is meta-schema, not project content** (M8 §1a) — `full`/`mid`/
`thin` ship as fixed values in the manifest's shape, the same way
`characters[]`/`archetypes[]` do, because the tier boundaries come from
capacity economics that hold regardless of genre, not from this game's
specific cast. The bad guy and any talking bosses are `characters[]`
entries in the project manifest (tier `full`/`mid`), exactly like
Selena — not a new data shape, just more entries.

The bad guy is **not** an archetype instance — he needs the same
treatment Selena got in M7 (dedicated bible, dedicated corpus,
persistent NPC Database entry), because he has to remember the player
across separate encounters and levels in a way no archetype-tier
instance needs to. Talking bosses sit in between: named, with a real if
smaller corpus, persistent only within their own local arc (this boss,
this dungeon branch) rather than the whole game.

**Full/mid tier characters get compositional features too, on top of
their dedicated corpus** (M9) — the bad guy isn't exempt from the
feature-tuple mechanism just because he also has a bible; his profile
features (age/gender/occupation-equivalent/personality descriptor) still
compose with his relationship state per player, the same mechanism, on
top of the dedicated voice content M7-style characters get that
thin-tier instances don't.

### 2. Seeded procedural instantiation — deterministic, not just varied

When the dungeon generator rolls a new level, any archetype-tier NPCs it
places must be instantiated from the *same* seed stream the level
generator uses — same discipline as M4's sampler, M8's instance
jitter, and M9's relationship-state randomization (xorshift32,
deterministic given a seed). Concretely: level seed → (level layout,
thin-tier NPC placements + their instance seeds) as one deterministic
derivation, not two independently-random systems that happen to run in
the same frame. This is what makes "seed N regenerates this exact
level, with this exact guard, saying creatures of this exact
personality jitter" testable at all — and it's the same bit-exactness
discipline the whole project already runs on for the model itself.

### 3. Lifecycle across the dungeon loop

Explicit rule, because it's easy to get wrong silently: **full and mid
tier NPCs persist across dungeon loop iterations** (the bad guy
remembers how many times you've died to him across separate runs; a
recurring boss remembers your last fight). **Thin-tier instances spawned
inside a generated level are ephemeral** — no durable NPC Database entry
survives past that level, they don't carry memory into the next loop,
and their conditioning is dominated by current-level state (mood/event)
rather than history. This keeps the NPC Database's persistent-memory
cost bounded by the *authored* cast (dozens, known in advance), not by
however many levels a long play session generates.

### 4. Mid-save-load determinism contract

If the player saves mid-level and reloads, a thin-tier instance must
either (a) say the exact same thing it would have on first encounter,
reproduced deterministically from the stored level seed, or (b) be
explicitly documented as allowed to drift, with a reason. Pick (a) by
default — it's free (the seed is already stored for level regeneration)
and it's consistent with the project's existing "no undocumented
nondeterminism" discipline. Don't leave this implicit; it's the kind of
gap that turns into a confusing bug report months later.

## Definition of done

- [ ] Three-tier system implemented: full / mid / thin, with the NPC
      Database schema supporting all three (persistent vs. ephemeral
      entries)
- [ ] The bad guy: full bible + corpus, persistent across encounters and
      loop iterations; added to the project manifest as a `characters[]`
      entry (tier `full`), same shape as Selena
- [ ] At least one talking boss: mid-tier bible + corpus, persistent
      within its own arc; added to the manifest as a `characters[]`
      entry (tier `mid`)
- [ ] Dungeon-level generation derives thin-tier NPC placement + instance
      seed from the same level seed (one deterministic derivation)
- [ ] Save/load determinism contract implemented and tested: reloading a
      level reproduces the same thin-tier instance dialogue
- [ ] Long-horizon consistency eval for the bad guy across a scripted
      multi-encounter session (Data Science Review)
- [ ] ROM boots, SELFTEST PASS, demo shows one procedurally-generated
      level with a thin-tier guard instance + the bad guy in two separate
      simulated encounters
- [ ] Docs: this file finalized with real numbers, README status row,
      tag `m10`

## What M10 deliberately does not do

- The full town cast build-out (shopkeeper/wizard/damsel/pub_patron
  archetypes) — M8 proved the mechanism on `guard`; filling out the rest
  of the roster is M11 content work, not new mechanism
- Toolkit packaging / portability documentation — M11
- Gossip between NPCs (needs the full town, not just one archetype +
  one villain) — M11

## Data Science Review — reviewing the engineering plan above

**The tier corpus budgets need to be derived, not asserted.** The table
above gives "full ~10MB, mid more-than-instance-less-than-full, thin
archetype-instance" as a *shape*, but the mid-tier number is currently a
placeholder with no empirical anchor. Recommend: before authoring a
boss's corpus, run the same divergence-metric methodology from M7/M8 at
a few candidate mid-tier sizes and pick the smallest one that clears a
"boss reads as distinct from both Selena/full-tier voice and from
generic archetype voice" bar — don't guess a number between two known
endpoints and call it done.

**New eval category: long-horizon consistency.** Nothing tested so far
covers a character across *many separate* encounters spread over a long
session with save/loads in between — Selena's M7 eval is continuous
within one scene, archetype instances in M8/M9 don't have memory to be
inconsistent about. The bad guy is the first character where this
actually matters (contradicting an earlier taunt, forgetting an
established score, resetting emotional tone between encounters would all
read as "not alive" even if any single line sounds fine). Concrete
proposal: a scripted synthetic-session eval — N simulated encounters
with known intervening events (player died twice, player found the
villain's stolen item, a session save/load in between) — checked by
human eyeball for continuity, not just per-line quality. This is a new
axis, not a bigger version of the per-condition eyeball check M4/M7
already do.

**Determinism contract for thin-tier instances is a correctness
requirement, not a nice-to-have, and it's cheap to verify.** Since the
level seed is already stored, add it to the golden-vector discipline
this project already runs everywhere else: pick a handful of level
seeds, record the exact thin-tier dialogue they produce, and let CI/host
tests catch any future change that silently breaks reproducibility — the
same "host-green implies console-behavior" logic the whole project is
built on, extended to procedural NPC placement.

**Watch the capacity-monitoring metric started in M8, continued in M9,
now with a sharper question.** M10 adds a full-tier character (the bad
guy) and at least one mid-tier boss to a shared model that's also
carrying Selena and M9's compositional archetypes. This is exactly the
scenario the original one-model-per-NPC-vs-shared-model tradeoff
discussion worried about: capacity dilution across *multiple full-tier
voices*, not just one voice plus thin archetypes. If Selena's or the bad
guy's own held-out divergence/val-loss measurably degrades when the
other is added to the same training run, that's the concrete, data-
backed trigger to split into two shared models (e.g., one for full/mid-
tier "named" characters, one for thin-tier archetypes) rather than a
single universal model — record this as the explicit decision rule, not
something to notice only if it becomes an obvious problem later. M9's
compositional mechanism should make this *less* likely to trigger than
it would have under M8's opaque-tag scheme (shared traits share
capacity instead of competing), but that's a hypothesis M9's own
capacity data should confirm before M10 assumes it.
