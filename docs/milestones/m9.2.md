# M9.2 — External review (Legend of Elya N64): evaluated, mostly not adopted, one targeted experiment run

**Status: INVESTIGATED.** A same-day-style follow-up to M9 (like M9.1),
prompted by an external email reviewing M9's results and suggesting four
ideas borrowed from a parallel N64 homebrew project, [Legend of
Elya](https://github.com/Scottcjn/legend-of-elya-n64) (`rsp_matmul.S` +
`matmul_rsp_drv.c`, `nano_gpt.c`, `train_sophia_v8.py`,
`reference_cli.c`). Ran in a remote session **without the Mac toolchain,
Ares, or local qwen/mlx_lm infra** — trainer-side work only (CPU, `uv run
pytest`/scripts); no ROM was built or booted this session. Where that
matters, it's called out below and left for the next Mac-toolchain
session per this project's own honesty discipline (don't claim a hardware
gate that wasn't actually run).

## Method

Each of the four suggestions was checked against the actual source it
referenced (fetched and read, not taken on the email's description alone
— the email is a secondary source and this project's own rule is to
verify claims against ground truth, e.g. the H=256 RSP figures in M9
being independently re-verified against the built `.elf` rather than
trusted from an earlier doc) and against this project's real, current
architecture (`core/`, `game/src/user/rsp_ngpt.S`, `docs/spikes/
rsp-matvec-h320.md`), then judged **adopt / reject / defer** with
reasoning — the same Data Science Review discipline M8/M9 already apply
to in-house proposals, applied here to an external one.

## 1. RSP matmul tiling patterns (`rsp_matmul.S` + `matmul_rsp_drv.c`) — DEFER, structurally already equivalent

Read the actual microcode. Elya's kernel: 4KB DMEM split into fixed
control/input/weight/output regions, tiles of **8 rows × 128 columns**
per invocation, weights stored int16 (CPU-side sign-extended from int8),
8-wide SIMD `vmulf`/`vadd` multiply-accumulate with a cascading
element-broadcast horizontal reduction, and — notably — **no in-ucode
DMA**: the CPU driver pre-loads DMEM before signaling the RSP, which then
only does `lqv` loads within DMEM.

64GPT's own kernel (`game/src/user/rsp_ngpt.S`, generalized to H=320 in
M9, `docs/spikes/rsp-matvec-h320.md`) already does the same fundamental
things: int8→int16 sign-extended weights, tiled to fit a 4096B DMEM
budget (`tile_rows = floor(2048/H)`, 6 rows at H=320), 8-wide RSP vector
multiply-accumulate. The two kernels independently converged on the same
approach because it's the approach the hardware forces (4KB DMEM, 8-lane
vector unit) — there isn't a distinct "Elya technique" to import that
this kernel doesn't already do.

**Why not adopt anyway, even as a possible micro-optimization:** M9's
kernel has **320 bytes of DMEM headroom out of 4096** (`docs/spikes/
rsp-matvec-h320.md`, confirmed against the real built `.elf`'s section
sizes, not an estimate) and is proven **bit-exact on real hardware**
(XCHK PASS) at that margin. Any change to it needs the same
hardware-in-the-loop verification the H=320 spike used (Ares boot,
screenshot, XCHK) — unavailable in this remote session (no Pyrite64/Ares
here). Touching a 320-byte-margin, hardware-verified kernel without the
ability to re-verify it on hardware is exactly the kind of risky,
hard-to-reverse action this project's own conventions caution against.
**Deferred, not rejected** — if a genuine improvement surfaces later
(e.g. Elya's fixed-region DMEM layout vs. this kernel's tile scheme, for
someone who wants to dig deeper), it needs a Mac-toolchain session with
Ares to test, same as every prior RSP change this project has made.

**M9.2 follow-up (2026-07-17, Mac-toolchain session): upgraded to
REJECT after independent verification.** A later session in this same
milestone had real Ares/toolchain access, so re-fetched both files
directly from source (not the prior session's summary) to close the
deferral out rather than leave it open indefinitely. Two structural
differences, not just stylistic ones:

- **Scope**: Elya's kernel handles at most **8 rows × 128 columns per
  invocation**, with the CPU driver issuing a fresh call (and a fresh
  DMA) per tile. 64GPT's kernel streams the **entire 960×320 matrix in
  one call** — `NgptMatvec` loops 160 tiles internally, with `jal
  DMAIn`/`DMAOut` issued *from inside the ucode itself*
  (`game/src/user/rsp_ngpt.S:167-196`), no host round-trip between
  tiles. 64GPT's is the more complete design of the two, not the
  simpler one.
- **Precision**: Elya's horizontal reduction uses `vmulf` (a 16-bit
  fractional multiply that rounds/truncates) followed by a `vaddc`
  pairwise lane-collapse — an *approximate* reduction, consistent with
  a project that already runs float32 activations elsewhere and doesn't
  need exactness. 64GPT's `DotRow` uses `vmudh`/`vmadh` to accumulate
  into the RSP's full 48-bit accumulator, then folds `ACC_HI`/`ACC_MD`
  per lane (`FoldLane`, `rsp_ngpt.S:128-149`) into an **exact int32**
  sum — zero rounding anywhere in the reduction.

Porting Elya's reduction here would trade this kernel's exactness for
no performance gain (both designs are already bound by the same 8-wide
SIMD hardware ceiling) — a strict downgrade against the one property
(bit-exact host↔RSP agreement, XCHK) this kernel exists to prove.
Verdict revised DEFER → **REJECT**; nothing here to adopt at any point,
not just "not yet." `rsp_ngpt.S` was not modified.

## 2. R4300i math primitives (`nano_gpt.c`: Taylor `exp()`, Quake fast inverse-sqrt) — REJECT, solves a problem this project doesn't have

Read the actual file. Elya's model runs **float32 activations** via
`-msoft-float` (software floating point, since the R4300i's hardware FPU
support is incomplete/unreliable for some ops in that toolchain) — the
Taylor-series `exp()` and Quake fast-inverse-sqrt exist specifically to
avoid calling `<math.h>` under a soft-float build, which would pull in
hard-float instructions the target can't run.

64GPT never has this problem, by a stronger design choice made all the
way back in M2: **zero floats anywhere in `core/`**, period (this
project's own hard constraint list, `CLAUDE.md`). Sigmoid/tanh are
integer LUTs emitted by the trainer as a single source of truth — no
runtime approximation, no soft-float emulation overhead at all, and
already proven bit-exact host→Ares→(pending)silicon. Elya's math
primitives are a well-engineered fix for a problem (soft-float on a
target with unreliable hard-float) that only exists because that project
chose to keep floats; adopting them here would mean **adding** float
handling this project deliberately never had, to then need a workaround
for it. Not a fit — recorded as a validation of the existing int-only
design, not a gap.

Same read applies to Elya's big-endian handling: it does runtime
magic-number detection (`magic_raw == SGAI_MAGIC || magic_raw ==
swap32(SGAI_MAGIC)`) and byte-swaps in place. 64GPT's blob parser
(`ngpt_read_u16be`/`u32be`, `docs/03-blob-format.md`) never needs to
detect or swap anything — it reads big-endian bytes directly regardless
of host endianness, by construction. Simpler, and already correct on all
three platforms this project targets (Mac, Ares, N64). Nothing to adopt.

## 3. Host reference CLI (`reference_cli.c`) — REJECT, already covered

Elya's host reference CLI exists to give a byte-exact comparison point
outside the N64 build. 64GPT already has this, and arguably a stronger
version of it: `trainer/ngpt_trainer/ref_impl.py` (integer NumPy,
mirrors the C engine's fixed-point math step-for-step) generates the
golden vectors that `cmake -B build tests && ctest` checks the C engine
against, byte-for-byte, on every host run — the same purpose Elya's CLI
serves, already wired into this project's actual TDD loop rather than a
separate manual tool. Nothing to add.

## 4. Personality-specific fine-tuning / dedicated response banks (`train_sophia_v8.py`) — ADOPT the mechanism (narrow); measured effect is INCONCLUSIVE

Read the actual trainer. Elya trains **one shared model** (not
per-character fine-tuning, despite the filename) and differentiates
voice with **persona-prefix conditioning** — exactly this project's own
compositional-conditioning mechanism (M9's `P:/D:/OCC:/R:/M:/C:/EV:`
tokens vs. Elya's `<|sophia|>`-style prefix tokens), independently
converged on. The one genuinely different data point: Elya backs each
persona with **50+ manually-authored responses per prompt, repeated
~220×** — a much heavier per-persona repetition than this project's
cast corpus (`per_combo=3` across 240 shared combos) or even guard's own
proven precedent (`GUARD_PER_COMBO=24` across ~45 combos/instance).

This lines up with a gap M9 already shipped with, honestly documented:
**Kragan specifically** was the one cast member that garbled live on
real hardware (`docs/milestones/m9.md` DoD: "GOTTAND", "RECAND",
"NONDS"), while Bram and Fergus came out clean — and Fergus is the only
one of the three that already had a small per-character catchphrase
bank (`_FERGUS_CATCHPHRASES`, M9). That's a real, if small, correlational
hint pointing at the same lever Elya leans on hard: per-character
reinforcement content on top of the shared compositional signal.

**What was done this session:** added `_KRAGAN_CATCHPHRASES` (8 short,
cold/bandit-flavored lines, same 0.3-probability inclusion mechanism as
Fergus's bank — `trainer/ngpt_trainer/cast_corpus.py`), with new tests
(`trainer/tests/test_cast_corpus.py`: catchphrases actually appear in
Kragan's generated lines, the two banks are disjoint). This is
deliberately the *narrow* version of Elya's idea — a small bank at the
same probability weight as Fergus's, not a 220×-repetition rewrite of
the whole corpus, which would reopen the still-unresolved M9 DoD item
(full capacity-dilution density sweep) this session has no time budget
for.

### Experiment: does it help?

`trainer/m9_2_kragan_catchphrase_experiment.py` — same cast-alone,
minutes-scale methodology as M9.1's density experiment (no Selena/guard
mixed in, so the same missing-Selena confound applies and is disclosed
here for the same reason M9.1 disclosed it: absolute quality is worse
than the shipped production model's, but the WITH-vs-WITHOUT
*comparison* should still be fair since the confound hits both variants
equally). Trained WITHOUT Kragan's bank (M9 baseline, `cc._CATCHPHRASES`
temporarily patched back to Fergus-only) and WITH it (M9.2, shipped),
same seed, H=320, combo-level holdout split. Sampled Kragan's trained
combos (2 seeds each, stochastic sampling per this project's own
"Model I/O testing" convention — greedy decoding collapses to one output
per prompt and would hide the exact variability this needs to see) plus
the `(bandit, gruff)` held-out generalization probe from
`cast_corpus.HOLDOUT_COMBOS`.

**Result: inconclusive, no clear win — recorded honestly, matching M9.1's
own epistemic discipline rather than being dropped or oversold.**

| Variant | Final val loss | Fully-clean trained-combo lines |
|---|---|---|
| WITHOUT Kragan bank (M9 baseline) | 0.2030 | 2 / 11 |
| WITH Kragan bank (M9.2) | 0.2024 | 4 / 12 |

Val loss moved by 0.0006 — noise, not a real signal (for comparison,
M9.1's own WIDE-vs-NARROW delta was 0.0086 and that was already called
inconclusive). The eyeball read is a genuinely mixed bag in *both*
directions, small-sample (11-13 lines each, one seed pair) and not
strong evidence either way:

```
WITHOUT: "I HAVE NO PATIENCE FOR THIS. I'M RIGHT HERE. I'M NOT GOING."
         (fully clean)
WITHOUT: "OKAY, SU'RE WAST'LL MY BACK. DID THAT ONE ABOUT? NO -- MY ALW
         YOUR WALKS OND LAFERERSTRONG BEFORM." (heavily garbled)

WITH:    "OKAY, OFF YOU GO, THEN. I'LL BE COUNTING THE MINUTES. NOT
         REALLY. MAYBE A LITTLE." (fully clean)
WITH:    "YOU'RE ALREADY WES! MYSTINGS COOD DOWN. CAME BE GOOD, YOU'RE
         ALREADY TESTING ME. OKAY THAT LAND TO NEVER. DEER BACK FROM
         WORT, NOT THEN. SIT YOURSELF DOWN, MAKE YOURDE FORM. I WATCH
         THIS ROAD DAY AND NIGHT. MY BLADE DOESN'T MISS. I'LL BE THERE
         FOR YOU." (heavily garbled around an intact catchphrase)
```

That last WITH example is the most informative single data point: the
literal catchphrase ("MY BLADE DOESN'T MISS") reproduces verbatim and
correctly — the bank mechanism itself works exactly as designed, the
model *did* learn the association — but the surrounding text in the same
line is still garbled. That's evidence against this specific lever
fixing the underlying problem: a small, low-probability (0.3) 8-phrase
bank can anchor its own content reliably without doing anything to
raise the fluency of the rest of the character's output. WITH did have
more fully-clean lines than WITHOUT in this sample (4/12 vs 2/11), a
mild directional hint, but on a sample this small and this noisy it
would be overclaiming to call that a real effect — the held-out
`(bandit, gruff)` generalization probe garbled in *both* variants,
about equally.

**Interpretation, consistent with M9's own root-cause note**: this
result doesn't contradict M9's existing hypothesis that Kragan's
garbling is a corpus-density problem at this model's ~400K-param budget,
not a missing-catchphrase problem — a single small bank at Fergus's same
modest weight was never a strong enough lever to move that, and this
experiment (honestly) shows it didn't. Elya's own precedent used ~220×
repetition, roughly two orders of magnitude more reinforcement than this
bank's 0.3-probability draw across ~2,160 pairs — the real, larger-scale
version of this idea (a much heavier Kragan-specific repetition weight,
not just a small bank) remains untested and is a real follow-up, not
what this narrow experiment tried.

### Honest scope of this result

This ran cast-alone (Selena/guard absent), matching M9.1's own
disclosed confound — it is evidence about the catchphrase-bank lever in
isolation, not a claim that the shipped production model (Selena + guard
+ cast, full corpus mix) will show the same delta. **No ROM was built or
booted this session** (no Mac toolchain/Ares available here) — the
actual test of whether this closes M9's live-hardware Kragan gap needs a
real retrain inside `make_m9_blob.py`'s production mix, a build, and an
Ares boot, same as M9's own DoD required for the original finding. That
step is recorded as a follow-up below, not silently assumed to have
happened.

## Hardware verification (2026-07-17, Mac-toolchain session)

Picked up where the remote session left off, with real Pyrite64/Ares
access. Retrained `make_m9_blob.py` fresh (cache-free) with
`cast_corpus.py`'s Kragan bank included in the real production mix
(36000 Selena + 240 thin-identity + 4320 guard + 2160 M9 compositional
pairs, 5.90MB), same H=320, same seed=0.

**Val loss: 0.1036** — *higher* than M9's originally-shipped 0.0985,
recorded plainly rather than only reporting favorable numbers. This
delta (0.0051) is smaller than M9.1's own already-inconclusive
WIDE-vs-NARROW delta (0.0086) but larger than this milestone's own
cast-alone A/B delta (0.0006) — plausibly CPU training run-to-run
variance (PyTorch's CPU BLAS threading isn't bit-deterministic across
runs even with a fixed seed) rather than a real regression *caused by*
the Kragan bank, but this session ran one retrain, not a controlled
A/B on the full production mix, so causation isn't established either
way — flagged as an open question, not asserted as a Kragan-bank
regression. Int-vs-float agreement 0.9827 (above the 0.95 gate), 3/3
generalization-holdout combos non-degenerate.

**ROM build:** clean (`rm -rf game/build` first, per this project's own
stale-`.o` ABI-mismatch lesson). RSP kernel DMEM footprint unchanged
(text 1160 / data 552 / bss 3224 — identical to the H=320 spike's
figures), confirming `rsp_ngpt.S` was not touched, as planned.

**Ares boot:** `SELFTEST PASS`, `RSP ON`, `XCHK PASS` on screen —
the on-device engine's output is proven byte-exact against the Python
reference for all 18 golden prompts, including a Kragan-flavored one
(`OCC:bandit`, part of `m9_golden_prompts`' random sample from the real
compositional corpus).

**The actual Kragan-gap question — does it still garble on real
hardware, full production mix, not just cast-alone?** The golden set
includes exactly this case, and because SELFTEST+XCHK passed, the text
below is proven to be the literal on-device output, not a Python
estimate:

```
P:man D:cold OCC:bandit R:acquaintance M:embarrassed C:damage-taken EV:low_health
-> OKAY FORGET INSTIT, LET ME SEE IT. NO, LET ME SEE -- OKAY YEAH, THAT'S A GREAT RIGHT YOU.
```

Garbled ("INSTIT" isn't a word; "THAT'S A GREAT RIGHT YOU" doesn't
parse), no catchphrase present in this particular sample, and Selena's
own live attract-mode line in the same boot was similarly garbled
("IT'S FISE", "WITHOUT ALL THE PICK") — the coherence gap is not
Kragan-specific at this val loss, it's showing up across characters
this run. **Conclusion: the Kragan-bank mitigation does not close M9's
known coherence gap, confirmed now at full production scale on real
hardware, consistent with this milestone's own cast-alone A/B finding.**
The M9 Known-follow-up item stays open — this session adds real
hardware confirmation of the cast-alone experiment's direction, it
doesn't reverse it.
