# 01 — The toolchain and Pyrite64

How code on your Mac becomes a running N64 ROM, layer by layer.

## The layer cake

```
┌────────────────────────────────────────────────┐
│ your game code        game/src/user/*.cpp      │  you write this
├────────────────────────────────────────────────┤
│ Pyrite64 engine       scenes, objects, assets, │  MIT, HailToDodongo/pyrite64
│ + editor              build system, CLI        │
├────────────────────────────────────────────────┤
│ tiny3d                3D ucode + model format  │  (unused by our text demo)
├────────────────────────────────────────────────┤
│ libdragon             kernel, display, input,  │  the open-source N64 SDK
│                       DFS filesystem, printf   │
├────────────────────────────────────────────────┤
│ MIPS cross-toolchain  gcc for mips64, ld, etc. │  installed once to
│                                                │  $HOME/pyrite64-sdk
└────────────────────────────────────────────────┘
```

- **libdragon** is the SDK: it boots the console, sets up video, and
  gives you C APIs. No proprietary Nintendo code anywhere.
- **Pyrite64** is a visual editor + runtime engine on top. We drive it
  mostly headlessly; the editor is needed once to create the project and
  attach the script, and any time you want to edit scenes.
- On macOS we use the Apple Silicon fork
  [proverbiallemon/pyrite64-mac](https://github.com/proverbiallemon/pyrite64-mac)
  (upstream supports Windows/Linux). **Pin the fork's tagged release** —
  Pyrite64 is early-dev and makes breaking changes; the pinned version
  lives in the root README.

## One-time install (macOS, ~30–60 min, attended)

1. `brew install cmake ninja git-lfs`
2. Clone pyrite64-mac at its pinned tag and launch it.
3. In the **Toolchain Manager**, run the install. It fetches and builds
   the MIPS toolchain + libdragon + tiny3d into `$HOME/pyrite64-sdk`
   (no sudo, no env vars to set) and installs the **Ares** emulator via
   Homebrew. This compiles GCC from source — start it before lunch.

## Anatomy of a Pyrite64 project (our `game/` dir)

| path | owner | contents |
|---|---|---|
| `project.p64proj` | editor | project config (JSON) |
| `assets/` | you | textures/models/audio, auto-converted at build |
| `data/` | editor | scenes as pretty-printed JSON — don't hand-edit |
| `src/p64/` | build | generated glue (script/asset tables) — don't edit |
| `src/user/` | you | **all `.cpp` here are auto-compiled into the ROM**, one wildcard per subdirectory |
| `Makefile.custom` | you | your rules, `include`d by the generated Makefile |
| `build/`, `engine/`, `filesystem/`, `Makefile`, `*.z64` | build | artifacts, git-ignored |

Two facts we verified in Pyrite64's source and rely on:

- Only `*.cpp` files are compiled (the generated Makefile globs `.cpp`
  and maps only `.cpp` to objects). Hence `core/` is written as C-style
  C++ in `.cpp` files.
- The directory scan lists a symlinked directory but doesn't recurse
  into it. Hence `game/src/user/n64gpt → ../../core` works because
  `core/` is **flat**. Keep it flat.

## Building

GUI: the editor's build button. Headless (what we script and what CI
would run — a GPU isn't even required):

```sh
./pyrite64 --cli --cmd build /path/to/64gpt/game/project.p64proj
```

Output: `game/64gpt.z64`. Boot it:

```sh
ares game/64gpt.z64        # or open it from the Ares GUI
```

`--cmd clean` cleans. Running the CLI while the editor is open is
supported.

## How our model blob gets into the ROM

The editor's asset pipeline only converts file types it knows (PNG, GLTF,
WAV…). A raw binary would be ignored, so `model.bin` takes a side door,
verified against the generated Makefile's structure:

1. `game/rawfs/model.bin` is committed (regenerated by the trainer).
2. `game/Makefile.custom` copies it to `filesystem/model.bin` and makes
   the `.dfs` target depend on it.
3. The DFS packer bundles the whole `filesystem/` dir into the ROM.
4. At runtime: `asset_load("rom:/model.bin", &size)`.
