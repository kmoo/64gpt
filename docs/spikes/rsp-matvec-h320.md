# Spike: generalizing the RSP matvec kernel to H=320 (M9) — VERDICT: RSP/CPU BIT-EXACT ON HARDWARE

**Branch:** `worktree-rsp-spike-h256` (this spike's kernel work continues
directly from the H=256 generalization recorded in
`docs/spikes/rsp-matvec-h256.md`). **Question:** does the RSP matvec
kernel generalize past power-of-2 hidden sizes — H=320, M9's real-margin
capacity target (`docs/milestones/m9.md` §6) — and does the RSP path
still compute bit-identical results to the CPU path at that size?

## Why this is a harder case than H=128->256

Both prior spikes (H=128, H=256) doubled a power of 2, so `tile_rows =
2048 / H` was always an exact integer and `W_TILE` could be pinned at a
constant 2048B by construction. 320 does **not** divide 2048 evenly —
this is the first time the kernel has needed a real "does H divide the
DMA budget cleanly" check rather than an idealized continuous formula,
exactly the gap `docs/milestones/m9.md` §6 flagged before any hardware
work started ("the real per-H constant needs computing precisely, not
just plugging into the idealized formula").

**Resolution:** `tile_rows = floor(2048/320) = 6` (not exact — 6*320 =
1920B, *less* than 2048B, which means more headroom, not less, as long
as the row count divides evenly by the tile depth). 3H = 960 rows total;
960/6 = 160 tiles exactly, no remainder tile needed. H=320 is still a
clean multiple of 16 (320/16=20) and the resulting half-width a multiple
of 8 (160/8=20), so the SIMD unpack/accumulate loop *structure* is
unchanged from H=256 — only iteration counts scale.

The row-address multiply also stops being a single shift: 256 and 128
are both powers of 2 (`row * H` = `row << log2(H)`), but 320 isn't.
Decomposed as `320 = 256 + 64 = (1<<8) + (1<<6)`, so `row * 320` becomes
two shifts and an add — exact, cheap (executes once per row, tile depth
is only 6), and the same decomposition generalizes to any H that's a
short sum of powers of 2, which covers every H this project has used or
is likely to use next.

## Verdict (2026-07-17, Ares, on-screen, real build)

| gate | result |
|---|---|
| DMEM budget | **FITS** — 3224B .bss (W_TILE 1920 + W16_BUF 640 + H_BUF 640 + OUT_TILE 24) + 552B .data = 3776B / 4096B, confirmed via the built `.elf`'s actual section sizes (`text 1160  data 552  bss 3224  total 4936` — the DMEM-relevant figure is data+bss, not the toolchain's combined total, which also counts `.text`'s separate 4096B IMEM budget) |
| XCHK (CPU-only generation vs RSP-enabled generation, same seed, same real H=320 model, on-device) | **PASS** — this is the actual question this spike exists to answer, and it's a direct byte-for-byte comparison computed live on hardware, not against an external reference |
| SELFTEST (2 throwaway goldens vs. this session's random-weight test blob) | **FAIL** — see caveat below; not evidence against the kernel |
| Build hygiene | one real bug found and fixed: a full clean rebuild was required (`rm -rf game/build`) because Pyrite64's incremental build reused `.o` files for `ContextBuilder.cpp`/`EventBus.cpp`/`WorldState.cpp` from *before* this worktree's merge with M8's `NPCDatabase::NPC` struct changes (added `personality[]`/`memorySlot`), causing a real ABI mismatch — first boot crashed with a `CPU Exception` reading address `0x73656C65`, which decodes as ASCII `"sele"` (part of `"selena"`) leaking into a pointer slot from the stale/fresh struct-size mismatch across translation units |

**Why XCHK is the load-bearing result here, not SELFTEST:** this spike
used a throwaway blob — random untrained int8/int32 weights at H=320,
generated by `trainer/make_m9_rsp_spike_blob.py`, specifically to prove
kernel correctness *before* real M9 training exists (mirrors both prior
spikes' own sequencing: mechanism proven cheap and fast, corpus/training
committed separately). XCHK compares the RSP path against the CPU path
**for the same loaded model, in the same ROM run** — it is a direct,
self-contained proof that the RSP ucode computes the same numbers as the
reference C engine, independent of whether those numbers mean anything
linguistically. SELFTEST instead replays generation against *externally
precomputed* Python goldens (`ref_impl.py`'s `generate_sampled()`) — a
mismatch there means the on-device engine diverged from the Python
reference, which is a different question, and a real hypothesis for why
it failed here specifically (and not for M2-M8's real trained models,
where this exact same golden mechanism has reliably passed): uniform
random, untrained logits are the adversarial case for top-k sampling —
near-ties between logits are far more common with random weights than
with gradient-shaped trained weights, so any surviving edge case in
either the Python reference or the C engine's rounding/tie-breaking is
far more likely to surface here than it would against real trained
weights. Not chased down further since it's off this spike's critical
path (proving the RSP kernel, not proving the golden-generation
methodology, which M2-M8 already validated repeatedly against real
models) — flagged here rather than silently ignored.

## What changed from the H=256 kernel

1. **Tile depth is no longer derived from a constant `W_TILE` size** —
   `tile_rows = floor(2048/H)` instead of an exact division, since H no
   longer divides 2048. This is *more* conservative than the H=128/256
   kernels (they used exactly 2048B; H=320 uses only 1920B), which is
   why the real DMEM headroom (320B) came out slightly better than the
   idealized formula's estimate (~190B) in `docs/milestones/m9.md` §6.
2. **Row-address arithmetic is shift+shift+add, not a single shift** —
   the first time this kernel has needed it, since H=320 isn't a power
   of 2.
3. **Unpack/accumulate loop iteration counts scale from H=256's 16 to
   20** (H/16), same loop *shape*, just more of it — no new instructions,
   the same primitives the H=128 kernel's bug ledger already paid for.

Game-side (`DialogueDemo.cpp`): buffer sizes and `rspBackendInit()`'s
guard now derive from a single `RSP_H` constant instead of scattered
literal `256`s, so the next H change (if any) touches one line instead
of six.

`core/ngpt.h`'s `NGPT_GRU_MAX_HIDDEN` raised 256 -> 320 in the same pass
(frozen-interface change; M9's H≈320 target was explicitly approved
mid-session, treated as the sign-off this change needed) — re-derived
the int32 hot-loop overflow bound while at it: `320 * 127 * 32767 ≈
1.33e9`, ~62% of int32's signed range, comfortably safe but past the old
comment's `< 2^30` claim, so the comment was corrected rather than left
to silently understate the real margin.

## Adoption

Real production adoption is gated on M9's actual trained corpus landing
first — this spike proves the kernel, not the model; `game/rawfs/
model.bin` was temporarily swapped for the throwaway test blob during
this spike's boot verification and restored to the real M8 model
immediately after, so nothing here ships until M9's real training run
produces an H=320 blob to replace it. See `docs/milestones/m9.md`'s
Definition of Done for the remaining steps (corpus, retrain, capacity
re-check).
